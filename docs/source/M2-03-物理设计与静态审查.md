# M2-03｜电商 OLTP 物理建模 V1.0：设计说明与静态审查

> 状态：**候选 DDL 已生成；结构性静态检查通过；数据库部署未进行。**
> 设计依据：本对话确认的 21 张 `biz_*` MySQL 业务／事件表、无 Outbox、行为数据独立 Kafka；**不采用**虚拟机中已有的 `001_ecommerce_oltp_candidate.sql`、固定种子或旧生成器。

## 1. 交付与边界

- 主文件：`001_ecommerce_oltp_v1.sql`。目标 MySQL **8.0.46**、现有数据库 `ecommerce_oltp`，InnoDB、utf8mb4，业务时间为 Asia/Shanghai 的 `DATETIME(3)`；连接会话的时区必须显式配置，避免跨系统误读。
- 仅定义 21 张新表，并在它们创建完毕后给新建的 `biz_coupon` 补 2 个指向 `biz_order` 的外键。不含 `DROP`、`TRUNCATE`、数据清理、存量表修改、初始数据或实际执行。
- **尚未在真实 MySQL 运行语法验收**。静态检查只检查文本结构、依赖顺序、命名等，不能等价于 MySQL DDL 执行成功或业务逻辑通过。
- 这些表与现有 `ecommerce_oltp` 中的 `cdc_smoke_test`、`cdc_user_test`、`datax_user_test` 不重名；执行前仍必须现场检查完整表名是否变化。
- 事件表由生成器或业务服务与当前状态在**同一 MySQL 事务**内写入；CDC 只采集需要的 MySQL 业务表，**不使用 Outbox**。行为 PV／商品交互／购物车交互另外进入 Kafka 三组 Topic，不建立 MySQL 行为事件表，也不为 Session 增加持久化表。

## 3. 数据库已能约束的内容

- 关键身份／业务 ID 使用 `BIGINT`，业务码及不可重放事件键设置唯一；会话键暂用 `VARCHAR(64)`。
- 所有人民币金额存储为 `BIGINT` **分**，不使用浮点金额；商品、订单、退款等金额拥有行级范围和方程检查。
- `biz_cart`、`biz_order` 的游客／注册用户所有者必须恰好有且只有一个；MySQL 唯一索引允许多个 `NULL`，因此两列分别唯一与 XOR 约束配合使用。
- 订单 `(order_id, sku_id)` 唯一；购物车 `(cart_id, sku_id)` 唯一；购物车数量在 1～99。
- 订单、支付、退款和优惠券状态字段均有 `CHECK`；订单金额 = 原价 - 优惠；订单明细原价 = 单价 × 数量。
- 退款当前记账字段满足已退 + 预留 ≤ 订单明细应付，已退数量 ≤ 购买数量。
- 支付成功订单通过生成列 + 唯一索引保证最多一次成功；退款成功申请同理。不同尝试各有独立资金业务 ID，支付回调、事件有唯一幂等键。
- 退款申请通过复合外键保证 `order_item_id` 确实属于 `order_id`；退款事件的资金交易也通过复合外键匹配申请。
- 券实例状态、关联订单 ID 与时间戳保持单行结构一致；订单券使用关联需事务校验。

## 4. **必须在应用事务／生成器测试中强制的规则**（不能冒充 DDL 已覆盖）

| 不变量 | 推荐实现与验收 |
|---|---|
| 订单必须恰有 1～5 条不同 SKU | 事务内插入订单与明细并校验条数，异常回滚；`UNIQUE(order_id,sku_id)` 只能防重复，不能保最少／最多行数。 |
| 订单金额、分摊守恒 | 按明细排序的确定性分配尾差，事务核验 `SUM(gross/discount/payable)` = 订单头；不允许以当前 SKU 价格重算历史订单。 |
| 订单创建后 15 分钟到期 | 服务生成 `payment_deadline_at = created_at + INTERVAL 15 MINUTE`，时间比较与 SQL 校验；DDL 仅验证截止时间晚于创建时间。 |
| CREATED→PAID／CANCELED、支付后不可取消 | 对订单 `SELECT ... FOR UPDATE`、状态条件更新；事件表同事务，行级 CHECK 不验证历史迁移。 |
| 支付重试／重复回调 | 重试更换 attempt/funding ID，重复同一资金回调复用 ID；资金成功金额=订单应付、时点在支付窗口内；零元订单如何结算尚须独立定口径。 |
| 券锁定／核销／取消释放／过期 | 锁券、建订单、写事件同事务；核销随支付成功，取消根据**取消时刻**转 UNUSED/EXPIRED，退款不返券；订单券用户归属、模板门槛／发放上限需校验。 |
| 多次部分退款 | 锁订单明细，申请预留额度；成功后释放预留并转累计已退，失败释放；单申请完整成功或失败；只有显式 `refund_quantity` 成功才累计数量。 |
| 历史数据版本 | 商品变更写状态＋`biz_product_change_event`，身份修订保留多版本并检查时间窗不重叠和强证据；禁止根据同设备跨账号强制合并。 |
| 购物车登录合并 | 锁两个购物车，按 SKU 聚合、上限 99、截断明细及操作 ID 一事务写入；核验两个购物车所有者。 |
| 实时与离线去重 | DataX 历史读取和 CDC 初始快照不能直接 UNION；必须设计一致性切换点、自然键与时序去重。 |

**历史回填提示**：对 `biz_user` 等只保留当前态的表，若只在 90 天数据全部导入 MySQL 后才启动 CDC，则 CDC 初始快照不能逆推出曾发生过的用户属性变化。要么在生成期同步采集各次变更，要么补充明确的历史重建方案；商品与订单等已有专用事件表可以保存所覆盖的变化。行为流要有 Kafka→HDFS 离线归档方案，否则 90 天 PV 无法直接由 DataX 从这些 21 张表提取。

## 5. 当前仍需在下一阶段确认／落地的细节

1. **新环境安全**：与 VM 候选文件同名空间完全隔离创建新文件；部署前检查 `biz_*` 是否已经存在，确认目标库、备份／回滚与用户权限。不可使用 `CREATE TABLE IF NOT EXISTS` 掩盖碰撞；请勿运行旧的候选 DDL。
2. **金额为 0 的订单**：表允许 0 元应付；是否免支付直达 PAID，或拒绝创建 0 元订单，现有业务讨论尚未最终确定。生成器暂不得制造这一未定义路径。
3. **版本与数据归档**：身份映射版本的全局编号／会话级关联和冲突处理必须落为测试；补充行为 Topic 的留存和历史归档方案。
4. **长事务和现金结果**：跨外部支付系统不可能单一 MySQL 事务覆盖第三方资金执行；只能在已核实成功回调后，在数据库内部原子提交相关状态和事件。
5. **索引负担**：本版首要保证可解释性，订单明细／退款事件的部分复合唯一键是为了复合 FK；在 MySQL 实测 `SHOW INDEX` 后再裁剪冗余索引，不能未经核实删除被 FK 使用的索引。
6. **持续造数**：新 Generator 不建设独立的约 100 单 Smoke 数据档位；直接生成 90 天正式数据规模，业务验收通过后再生成独立性能实验规模，并继续支持稳定实时增量。历史业务写库与行为事件写 Kafka 的时间和身份语义一致。
7. **故障与幂等**：事件表是业务变更历史，不等于额外可累加的第二份支付／退款事实；CDC 重复投递按业务键去重。

## 6. 推荐的下一个执行顺序（仅计划）

1. 用户确认本版字段／约束以及零元订单等未定义口径；**不自动部署**。
2. 以隔离 MySQL Schema 做真实 DDL 语法与 `SHOW CREATE TABLE` 验收，并故意插入非法数据验证关键约束。该步骤需另行确认库名与是否允许创建测试数据库。
3. 生成新代码目录的固定样例、业务事务和校验器；不读取或覆盖 VM 旧版 generator。
4. 固定种子验收、批量历史、实时增量依次通过后，再推进 ODS 口径和离实时一致性设计。
