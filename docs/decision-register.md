## DR-001：DataX 直写 Hive ODS 对应 HDFS 分区

- 状态：`accepted`
- 决策日期：2026-09-04
- 决策人：用户
- 影响范围：离线架构、Milestone 1、3、6、质量与对账
- 替代决策：无

### 背景

原离线架构在 DataX 与 Hive ODS 之间设置独立的 HDFS landing/staging Text/CSV 数据层。用户要求删除该独立层，同时保留 DataX 和以 Hive/HDFS 为核心的离线数仓主线。

### 决策

保留 DataX，并使用 HDFS Writer 直接写入 Hive ODS 对应的 HDFS 业务日期分区，输出目标为 ORC + Snappy。Hive ODS 同时表示 Hive 逻辑表和其 HDFS 物理存储；ODS 装载负责显式分区注册、`business_date`、`extract_time`、`batch_id`、`source_table` 审计字段、幂等发布和失败隔离。不建设独立持久化的 Text/CSV 中间数据层。

### 理由

该方案满足删除独立中间层的要求，同时保留 DataX 的批量抽取职责和 Hive ODS 的正式数据分层。未采用 Spark JDBC 替代 DataX，因为这会超出本次架构调整范围；未采用只删除流程图节点但不重定义写入责任的方案，因为它会造成 ODS 所有权、格式和验收边界不清。

### 验证方法

Milestone 1 验证 DataX、HDFS 和 Hive 的候选版本组合及最小写入/读取能力。Milestone 3 使用固定 MySQL 输入验证 HDFS Writer 的 ORC + Snappy 输出、Hive 分区可见性、四个审计字段、源表与 ODS 对账、首次运行、同日重跑、连续回补、异常批次保护和失败时非零退出状态。只有真实验证通过后，该路径才能标记为 `verified`。

### 影响与风险

DataX HDFS Writer 的格式、依赖和文件行为尚未在目标 ECS 环境验证。直接写 ODS 还要求明确批次发布原子性、临时文件处理和失败回滚；这些内容是 Milestone 3 的实现与验收责任，当前决策不构成运行证明。

### 回滚方式

若 Milestone 1 或 3 证明直写方案不可行，保留失败日志、版本、配置和固定输入，新增后续决策记录替代本决策，并经用户评审后调整架构；不得静默恢复旧链路或改用 Spark JDBC。

## DR-002：Agent 答复总结与记录确认门禁

- 状态：`accepted`
- 决策日期：2026-09-04
- 决策人：用户
- 影响范围：协作规则、变更日志、决策治理、Milestone 0
- 替代决策：无

### 背景

项目需要在每轮协作结束时明确本轮实际执行的核心操作和形成的核心决策，并由用户控制这些内容是否成为仓库内的正式记录，避免关键变化遗失，也避免把普通讨论自动升级为项目事实。

### 决策

Agent 每次最终答复必须简要总结核心操作和核心决策，并询问用户是否将本轮总结写入 `CHANGELOG.md`、`docs/decision-register.md` 或两者。除用户已在当前请求中明确授权记录的内容外，未获得确认前不得自动写入。确认后，只有可交付变更写入 `CHANGELOG.md`，只有影响范围、业务口径、架构、版本、模型、接口、安全或验收方式的正式决策写入 `docs/decision-register.md`；同时符合两类用途时可以分别记录。

### 理由

该规则让用户保留正式记录的最终控制权，同时通过固定的答复收尾降低遗漏重要变更和决策的风险。按文件职责筛选内容能够避免修改日志退化为对话流水账，也避免决策记录被一般操作淹没。

### 验证方法

静态检查 `AGENTS.md`、`README.md`、`docs/spec.md` 和 `docs/plan.md`，确认两个文件的路径、职责、答复总结要求和用户确认门禁一致。后续每轮协作通过最终答复及用户确认记录抽查该规则是否被遵守；该静态检查不证明未来答复已经执行规则。

### 影响与风险

所有 Agent 答复增加固定的总结与确认步骤。若不按文件职责筛选，可能造成重复记录或无效噪声；若用户未确认却自动写入，则会把尚未采纳的讨论误记为项目事实。

### 回滚方式

若该流程影响协作效率，由用户确认新的收尾或记录方式，新增决策替代本记录，并同步更新 `AGENTS.md`、`README.md`、`docs/spec.md` 和 `docs/plan.md`；不得直接删除历史决策。

## DR-003：Milestone 0 验收与 Milestone 1 门禁开放

- 状态：`accepted`
- 决策日期：2026-09-04
- 决策人：用户
- 影响范围：项目状态、阶段顺序、Milestone 0-1
- 替代决策：无

### 背景

Milestone 0 的项目范围、离线架构、模块边界、指标数量、实时状态、Project 2 只读边界和阶段计划已经完成文档修订及静态一致性检查。用户在评审首轮结果后指示继续执行状态收尾。

### 决策

Milestone 0 状态改为 `completed`。Milestone 1 保持 `pending`，但其 Milestone 0 前置门禁已满足，可以开始基础设施与兼容性工作。`completed` 是 Milestone 验收状态，不提高任何组件、配置、任务或数据链路的证据等级。

### 理由

文档基线已经满足 Milestone 0 的交付和评审要求，而组件兼容性及运行验证属于 Milestone 1 及后续阶段。把 M0 完成和运行对象 `verified` 分开，可以在推进阶段的同时保持证据边界真实。

### 验证方法

静态核对 `README.md`、`AGENTS.md`、`docs/spec.md` 和 `docs/plan.md`：M0 均为 `completed`，M1 均为 `pending` 且注明进入门禁已满足；旧离线中间层引用保持为零；30 项正式指标、10 项扩展指标、5 项实时候选和六个 Project 2 只读契约数量不变；执行编码、换行和 `git diff --check` 检查。

### 影响与风险

下一阶段允许开展主机、网络、磁盘、JDK 和组件兼容性验证，但不得把 M0 的文档验收当作安装、启动、连通或链路运行证明。业务模型、指标口径、精确版本和实时细节中的未决事项继续保持原状态。

### 回滚方式

如果后续发现 M0 基线存在影响 M1 的冲突，停止 M1，保留已取得证据，由用户确认后新增决策记录并将 M0 重新置为 `in progress` 或 `blocked`；不得修改或删除本历史决策。

## DR-004：Milestone 2 受限预设计例外

- 状态：`superseded`
- 决策日期：2026-09-04
- 决策人：用户
- 影响范围：阶段门禁、业务模型预设计、Milestone 1-2
- 替代决策：`DR-008`（自 2026-09-09 起替代 M2 保持 `pending` 和仅限预设计的边界）

### 背景

Milestone 1 的进入门禁已经开放，但尚未实际启动。用户希望暂缓 Milestone 1 并先推进 Milestone 2；现行阶段计划则要求 MySQL 先通过 Milestone 1 的启动和连接验证，且禁止在门禁未满足时创建正式业务模型和运行性产物。为在不虚构环境能力、不改变强制顺序的前提下提前收敛业务问题，需要定义一个边界明确的文档预设计例外。

### 决策

Milestone 1、2 均保持 `pending`，允许先创建和维护 Milestone 2 业务设计文档（现路径为 `docs/milestone-2-business-design.md`）。当时的受限设计只整理五个主题的业务过程、概念关系、30 项正式指标的过程依赖、验收场景和 `DECISION_REQUIRED`，不构成正式进入 Milestone 2。

预设计期间不得创建或修改正式 DDL、seed、数据生成器、测试程序、运行脚本、字段类型、状态枚举或可执行接口；`mysql/ddl/`、`mysql/seed/` 和 `mock/` 继续保持占位状态，不创建 `generator/` 或 `tests/`。只有 MySQL 通过 Milestone 1 的启动和连接验证，且 OLTP 表、字段、主外键、状态机和硬删除策略经用户确认后，才能正式进入 Milestone 2。

### 理由

该方案允许在暂时无法或不准备实施基础设施时先完成业务问题梳理，同时保留环境验证、业务确认和正式实现之间的证据边界。未采用直接把 Milestone 2 标记为 `in progress` 的方案，因为其进入条件尚未满足；未采用生成不可执行候选 DDL 的方案，因为候选字段和状态容易被误当成已采用模型，并会绕过必须由用户确认的业务语义。

### 验证方法

静态核对 `AGENTS.md`、`README.md`、`docs/spec.md` 和 `docs/plan.md`：Milestone 1、2 均为 `pending`，预设计允许范围、禁止范围和正式进入条件一致。执行 `git diff --check`；检查 `mysql/ddl/`、`mysql/seed/` 和 `mock/` 没有新增运行性内容，`generator/`、`tests/` 不存在；确认 30 项正式指标、10 项扩展指标、5 项实时候选和六个 Project 2 只读契约范围未改变。上述检查只证明文档和门禁一致，不证明 MySQL 或任何数据模型已经运行。

### 影响与风险

该业务设计文档会成为后续业务确认的输入，但其中所有对象关系仍为 `draft`。若读者忽略状态说明，可能误把概念关系当成物理模型；因此所有未确认内容必须显式标记 `DECISION_REQUIRED`，README、规格和计划必须持续说明该活动不属于正式 M2 实施。

### 回滚方式

若用户决定停止预设计，新增后续决策将本记录标记为 `superseded`，同步移除四份治理文档中的例外入口并恢复“当前只推进 M1”。业务设计文档保留为未采用的 `draft` 历史输入，除非用户另行明确授权删除；不得覆盖或删除本决策记录。

## DR-005：采用当前 ECS 集群记录作为 Milestone 1 确认事实基线

- 状态：`accepted`
- 决策日期：2026-09-04
- 决策人：用户
- 影响范围：事实来源、证据状态、集群配置、Milestone 1-2
- 替代决策：补充 `DR-003`、`DR-004`，不改变其历史状态；其中 M2 保持 `pending` 和受限预设计的边界由 `DR-008` 替代

### 背景

Milestone 1 原计划从三节点主机、网络、磁盘、Java 和 Hadoop 的现场盘点开始。用户随后提供 `alibaba-ecs-hadoop-cluster-rebuild-spec.md`，并确认该文件是本项目当前集群的实际搭建记录，不是通用参考方案；文件中的 `CONFIRMED` 可以作为当前确认事实。

来源快照日期为 2026-09-04，SHA-256 为 `0556E06CBF754D01E4CCD451356E0EB15F6BE6A3E7B49E91632FA85313F25264`。文件包含杭州地域、VPC/vSwitch、三节点私网地址和规格、`yee` 用户、`/data` 磁盘布局、OpenJDK 17/11 分工以及 Hadoop 3.4.1 的 HDFS/YARN 运行拓扑。

### 决策

把来源文件的状态按以下方式纳入 Project 1：

- `CONFIRMED` 直接作为当前集群确认事实，不降级为候选，也不要求重新证明事实是否存在。
- `CONFIGURED` 作为已采用配置，但不自动补足来源明确缺失的功能测试证据。
- `PLANNED` 保持候选或计划状态，不描述为已安装或已验证。
- `UNKNOWN` 必须现场获取，不猜测、不复制其他节点值，也不把秘密或阿里云账号级资源写入 Git。

Milestone 1 状态改为 `in progress`。现有 Ubuntu、网络、磁盘、用户和 Hadoop 拓扑不重新初始化；组件统一沿用 `yee`、`/data/software`、`/data/module` 和 `/data/<component>`。默认 Java 为 OpenJDK 17，Hadoop 3.4.1 单独使用 OpenJDK 11。NameNode 已存在，禁止再次格式化。

Hadoop 的版本、进程和拓扑已确认，但完整 HDFS 固定文件校验、MapReduce 输出和重启恢复证据尚未保留，因此 Hadoop 整体暂记为 `implemented`；补齐后才能标记 `verified`。`DR-004` 的 M2 文档预设计例外在 M1 为 `in progress`、M2 为 `pending` 时继续有效，允许和禁止范围不变。

### 理由

该记录来自本次项目集群的实际搭建过程，重复把确认事实降级为未知会造成无意义的重建风险，尤其可能误触现有 NameNode 格式化。按来源状态分别处理，既保留用户确认的事实，也不会用进程和静态配置替代项目要求的最小任务与重启证据。

未采用整份复制外部文件的方案，因为其中包含复建说明、Project 2 规划和不得进入 Git 的现场值类别；仓库只提取 M1 所需事实，并保存来源、哈希、适配和验证边界。

### 验证方法

静态核对 `docs/cluster-baseline.md`、兼容性矩阵、README、规格、计划和架构中的节点、私网地址、用户、目录、Java 与 Hadoop 拓扑一致。执行 `scripts/m1/collect-hadoop-evidence.sh`，固定输入为两行 UTF-8 文本，预期 HDFS SHA-256 一致、MapReduce `wordcount` 为 `alpha=2`、`beta=2`、`gamma=1`、退出状态为 0，并保存 YARN application ID 和聚合日志。评审通过后执行带精确确认参数的受控重启脚本，预期恢复 2 个 Live DataNode、2 个 RUNNING NodeManager 和 `hadoop201` 的四个控制进程。

上述补测用于满足项目验收，不否定来源中的确认事实。没有执行 ECS 脚本前，仓库改动最多证明 M1 验证入口已 `implemented`。

### 影响与风险

M1 从“准备开始”变为实际实施，并从 Hadoop 补证门禁继续。外部来源路径不属于仓库，若原文件后续变化，必须重新计算哈希并评审差异；不得用同一路径下的新内容静默替代当前快照。

### 回滚方式

## DR-009：M2 身份、会话与用户分类基础语义

- 状态：`accepted`
- 决策日期：2026-09-09
- 决策人：用户
- 影响范围：用户与流量模型、指标口径、M2.1-M2.4
- 替代决策：无

### 背景

M2.1 必须先确认用户与访客身份、会话边界以及新增、活跃、回流等基础语义，才能继续设计流量和用户主题模型。若这些规则保持未定，后续 OLTP 字段、固定验收数据以及 `P1_METRIC_001` 至 `018` 的去重与分类基础会产生歧义。

### 决策

`visitor_id` 与 `user_id` 分离，一个用户允许关联多个 `visitor_id`。登录前事件保留匿名身份且不追溯改写；登录后事件同时记录事件发生时的 `visitor_id` 和 `user_id`；登录动作本身不切断当前会话。

会话在连续 30 分钟无活动后重新开始，并在跨 `Asia/Shanghai` 自然日时强制切分。会话渠道取会话首次进入渠道；会话内渠道变化不拆分会话。

新访客和老访客按 `visitor_id` 首次访问日期是否等于业务日期判断并保持互斥。新增用户按注册日期等于业务日期判断。活跃用户是在业务日期内至少产生一次带 `user_id` 的访问、加购、下单或支付行为的用户。回流用户是此前活跃、连续 7 个完整自然日未活跃并在业务日期再次活跃的用户。新增用户与回流用户互斥，活跃用户集合可以包含两者。

新增下单人数和新增支付成功人数分别按个人首次有效订单日期和首次成功支付日期识别；有效订单与成功支付的具体状态范围继续由 `M2-DEC-006`、`M2-DEC-007` 和 `M2-DEC-009` 决定，本决策不提前补全。

### 理由

身份分离并保留事件发生时的标识能够避免登录后回写历史导致的口径漂移，同时支持一个用户跨设备或重置标识的常见情况。固定 30 分钟超时、自然日切分和首次渠道归属能形成可复现、易人工核对的离线会话规则。将活跃定义限定为可识别用户的实际业务行为，并明确回流观察窗口，可避免仅登录或注册状态造成分类歧义。

该方案不建设复杂身份图谱或跨设备自动合并，符合个人学习项目的实现和维护成本；实时事件的迟到、乱序与状态合并仍留到 Milestone 8 评审。

### 验证方法

M2.3 固定验收数据至少覆盖匿名访问后登录、一个用户关联多个 `visitor_id`、29 分钟与30分钟间隔、跨 `Asia/Shanghai` 零点、会话内渠道变化、新老访客互斥、新增与回流互斥、连续 7 个完整自然日未活跃后回流，以及个人首次有效订单和首次成功支付跨日的场景。M2.4 为相同输入生成确定性结果；M2.5 在真实 MySQL 核对源记录及预期分类。

相关指标只有在各自公式、事件字段和状态范围确认并于真实引擎核对后才能标记为 `verified`。文档一致性或静态测试不构成指标运行证明。

### 影响与风险

跨自然日强制切分会把持续跨零点的访问分成两个会话；会话渠道的首次归属不会反映同一会话中的后续渠道变化。登录前事件不回写意味着用户级分析不会自动吸收其登录前匿名行为。这些都是已接受的 V1 简化边界，后续模型和样例必须保持一致。

有效订单和成功支付状态尚未确认，因此 `P1_METRIC_017`、`018` 只能取得分类框架，不能形成最终公式。页面分类、具体事件字段和实时处理策略也不由本决策确定。

### 回滚方式

若固定验收数据或后续模型证明这些语义不适用，由用户确认后新增决策替代本记录，并同步更新 M2 业务设计、项目规格、指标口径、固定样例和受影响实现。不得直接改写历史决策或仅修改 SQL 造成文档与实现不一致。

## DR-010：M2 商品层级、加购与订单粒度

- 状态：`accepted`
- 决策日期：2026-09-09
- 决策人：用户
- 影响范围：商品与交易模型、业务键、指标基础、M2.1-M2.4
- 替代决策：无

### 背景

M2.1 需要确定商品层级、加购事件粒度、订单头与订单明细粒度及其幂等边界，才能继续设计支付、退款、金额守恒和 OLTP 物理模型。若 SKU、SPU、Category 和订单明细关系不明确，品牌、品类、SPU 订单指标及固定验收数据无法建立稳定归属。

### 决策

商品层级采用 Brand → SPU → SKU，Category 使用三级结构。一个 SPU 归属一个 Brand 和一个末级 Category，并可以包含多个 SKU；SKU 是商品详情浏览、加购和交易的最小商品单位。订单明细保存下单时的 Brand、Category、SPU 和 SKU 归属快照，商品主数据后续变化不改写历史订单。

一行加购事件表示一个行为主体对一个 SKU 的一次操作，区分新增、修改数量和移除，记录操作前和操作后数量。相同 `request_id` 的重复请求只生效一次；数量必须为非负整数，移除后的数量为 0。加购人数按事件发生时的主体去重：已登录使用 `user_id`，匿名使用 `visitor_id`，不追溯合并登录前行为。

V1 只有注册用户可以下单。一次结算生成一个订单头，一种 SKU 生成一条订单明细；一个订单可以包含多条明细，但不进行仓库、商家或物流拆单。`order_no`、`order_item_no` 分别作为订单头和订单明细业务键；相同下单 `request_id` 的重复提交返回原订单，不创建新订单。订单明细数量必须为正整数。

本决策当时未确定金额组成、有效订单状态、支付成功状态、取消或退款作用范围；其中 `M2-DEC-007` 至 `010` 后续已由 `DR-011` 确认，时间与金额规则仍由 `M2-DEC-011`、`012` 确认。

### 理由

以 SKU 作为最小可交易商品、SPU 作为商品聚合层，能够支持商品详情、加购和订单明细的一致关联。三级 Category 足以展示电商商品层级建模，同时避免为学习项目引入任意深度树的额外实现成本。订单时快照保证商品归属变化后历史指标仍可复现。

加购采用事件粒度可以保留新增、改量、移除和重复请求，便于离线与未来实时链路使用同一业务事实。订单不拆分符合 V1 不建设库存和履约域的范围，`request_id` 幂等与明确业务键可以覆盖重复请求验收而不引入额外服务架构。

### 验证方法

M2.3 固定验收数据至少覆盖一个 Brand 下多个 SPU、一个末级 Category 下多个 SPU、一个 SPU 下多个 SKU、商品归属变化后历史订单快照不变、加购新增/改量/移除、重复加购请求、匿名与登录主体、同一订单多条明细、重复下单请求和非法明细数量。预期结果必须证明业务键唯一、重复 `request_id` 不新增业务结果、订单明细快照稳定以及数量边界符合决策。

M2.5 在真实 MySQL 执行相关 DDL、seed 和测试后，核对约束、幂等输入、查询结果和失败退出。静态文档与候选 DDL 检查不构成运行验证。

### 影响与风险

V1 不支持游客下单，也不表达仓库、商家或物流拆单；这些能力不得从现有模型中推断。订单快照会产生一定字段冗余，但用于换取历史归属稳定。按事件时主体统计加购人数可能把同一自然人在登录前后计为两个主体，这是与 `DR-009` 不追溯合并边界一致的已知限制。

Category 固定三级会限制任意深度分类；若后续真实需求变化，不能仅修改表结构而不重新评审指标归属和固定样例。

## DR-011：M2 支付、逆向交易、状态机与删除策略

- 状态：`accepted`
- 决策日期：2026-09-09
- 决策人：用户
- 影响范围：交易模型、状态枚举、增量抽取、指标基础、M2.1-M2.5
- 替代决策：无

### 背景

M2.1 已确认订单头、订单明细和请求幂等，但支付尝试、取消、退单、退款、状态迁移及删除策略仍会直接影响源模型、金额守恒、DataX 增量完整性和退单指标。需要先固定这些业务边界，再设计物理约束和验收数据。

### 决策

一个订单允许多次支付尝试但最多一次成功，V1 不支持分次支付；成功支付金额必须等于订单应付金额。每次尝试使用独立 `payment_no`，相同 `request_id` 只创建一次。重复支付回调不得重复记成功或修改首次成功时间。支付成功人数按 `paid_at` 所属业务日期对 `user_id` 去重。

只有未支付的 `CREATED` 订单可以取消。支付成功后不能取消，只能进入退单和退款流程。退单业务单与资金退款分离；一条退单作用于一条订单明细，支持部分数量和多次退单，累计数量不得超过购买数量。退款关联退单、原订单和原成功支付，支持多次部分退款，累计成功金额不得超过成功支付金额。退单数以 `COMPLETED` 退单业务单为基础，商品归属使用原订单明细快照。

订单状态为 `CREATED`、`PAID`、`CANCELLED`、`PARTIALLY_REFUNDED`、`REFUNDED`；支付尝试和退款尝试状态为 `CREATED`、`SUCCESS`、`FAILED`；退单状态为 `APPLIED`、`APPROVED`、`REJECTED`、`COMPLETED`。`CANCELLED`、`REFUNDED` 是订单终态。退单只有在关联退款成功后才能进入 `COMPLETED`。支付或退款失败后若需重试，必须创建新的业务尝试记录。非法迁移必须拒绝且不修改原记录，合法状态变化必须更新 `update_time`。

用户、商品、订单、支付、退单、退款和优惠券禁止业务硬删除。主数据使用停用或软删除，交易数据保留原记录；加购事件保持 append-only，错误事件通过有效性标记处理。停用或软删除必须更新 `update_time`。V1 不建设周期性全量快照识别硬删除；固定测试数据只允许在隔离测试库整体重建。

金额组成、精度与舍入继续由 `M2-DEC-012` 确认，事件时间和跨日归属由 `M2-DEC-011` 确认，优惠券状态机由 `M2-DEC-013` 确认。

### 理由

多次尝试、最多一次成功的支付模型能够覆盖失败重试和重复回调，同时避免分次支付带来的额外金额分摊复杂度。把退单业务和退款资金分开，可以独立表达申请处理与资金结果，并支持部分、多次逆向交易和可解释的数量、金额守恒。

明确状态机和非法迁移行为有利于固定异常样例和后续数据库约束。禁止业务硬删除并让软删除更新 `update_time`，可以让基于更新时间的 DataX 增量捕获删除语义，避免为 V1 增加周期性全量快照和删除对账成本。

### 验证方法

M2.3 固定验收数据至少覆盖支付失败后新尝试成功、同单第二笔成功被拒绝、重复回调不改变首次成功时间、未支付取消、已支付取消被拒绝、单明细部分和多次退单、超数量退单、部分和多次退款、累计退款超限、无成功支付退款、非法状态迁移、终态后变更、软删除或停用更新 `update_time`，以及交易数据未被业务硬删除。

M2.5 在真实 MySQL 执行相关 DDL、seed 和测试，核对唯一性、引用、状态、累计数量与金额、幂等结果、`update_time` 和失败退出。静态文档、DDL 语法或候选测试不构成 MySQL 运行验证。

### 影响与风险

V1 不支持分次支付、支付后直接取消、游客下单或业务硬删除。支付或退款失败重试会产生新的尝试记录，后续指标和对账必须区分业务单与尝试流水。退单完成依赖退款成功，因此没有成功退款的已批准退单不会计入完成退单数。

禁止硬删除不能替代隐私合规的数据擦除方案；本项目只使用合成数据，若未来引入真实个人数据，必须新增安全与数据生命周期决策。金额字段、应付金额和退款金额精度仍未确认，当前累计上限只是业务约束，不是已实现数据库校验。

### 回滚方式

若物理模型、固定样例或 MySQL 验收证明这些规则不可行，由用户确认后新增决策替代本记录，并同步更新 M2 业务设计、项目规格、指标说明、DDL、seed、生成器和测试。不得直接改写历史状态机、用硬删除绕过增量设计或删除已有运行证据。

## DR-012：M2 时间、金额与优惠券语义

- 状态：`accepted`
- 决策日期：2026-09-09
- 决策人：用户
- 影响范围：时间与金额模型、优惠券状态机、`P1_METRIC_030`、M2.1-M2.5
- 替代决策：无；承接 `DR-011` 保留的时间、金额与优惠券待决策项

### 背景

`DR-009` 至 `DR-011` 已确认身份、会话、商品、正向与逆向交易、状态机和删除边界，但各过程的事件时间、跨日归属、金额精度、优惠分摊、累计退款以及优惠券状态仍未形成结论。这些语义直接阻断 M2.2 的字段、关系与约束设计，也使 `P1_METRIC_030` 缺少可实现的基础公式。

### 决策

所有业务时间统一按 `Asia/Shanghai` 解释并保留毫秒精度，具体 MySQL 类型留到 M2.2。业务日期必须由对应事件时间计算：页面访问使用 `event_time`，加购使用 `action_time`，订单使用 `ordered_at`，支付使用首次成功的 `paid_at`，取消使用 `cancelled_at`，退单完成使用 `completed_at`，成功退款使用 `refunded_at`，用户注册使用 `registered_at`。跨日过程分别归属各自事件日期；记录创建和更新时间只用于审计及增量抽取，不替代指标业务时间。数据到达时间与事件时间分开保存，迟到数据仍按事件时间归属。

V1 只支持人民币 `CNY`，金额保留两位小数并使用 `HALF_UP`。商品价格含税，不单列税额，运费固定为 `0.00`。数量为正整数，金额、优惠和退款不得为负。订单应付金额等于明细原价金额之和减去商品优惠和优惠券优惠，优惠不得超过订单原价；违反时拒绝创建订单。订单级商品优惠和优惠券优惠分别按明细原价比例分摊，舍入尾差按明细原价金额降序、`order_item_no` 升序分配，保证明细与订单金额守恒。成功支付金额必须等于订单应付金额。

部分退货使用累计法计算退款：累计可退金额为 `ROUND(明细应付金额 × 累计完成退货数量 ÷ 购买数量, 2)`，本次退款为累计可退金额减去此前成功退款金额。累计完成退货数量和累计成功退款金额不得超过购买数量和明细应付金额；全部商品完成退款后，累计成功退款金额必须等于订单应付金额。

V1 只支持可设置最低订单原价门槛的固定金额优惠券。只有注册用户可以领取和使用，一个订单最多一张券，一个领取实例最多成功使用一次。领取实例状态为 `CLAIMED`、`LOCKED`、`USED`、`EXPIRED`，允许 `CLAIMED → LOCKED → USED`、`CLAIMED → EXPIRED`；未支付订单取消后，未过期时 `LOCKED → CLAIMED`，已过期时 `LOCKED → EXPIRED`。有效期在锁券时检查，合法锁定后不因支付时间超过有效期而失效；支付成功后不因退单或退款返还。

`P1_METRIC_030` 定义为按首次成功支付 `paid_at` 业务日期统计的优惠券毛补贴率。分子为当日成功支付订单的优惠券优惠金额之和，分母为同一批订单的商品原价金额之和；后续退款不追溯修改。分母为零时输出 `0`，比率保留 4 位小数，百分比展示保留 2 位小数，使用 `HALF_UP`。净补贴率不纳入 V1。

### 理由

以业务事件时间而不是任务时间归属，可以稳定支持跨日、迟到和后续回补；统一业务时区与毫秒精度也便于对支付回调和状态变化排序。CNY 两位小数、含税价格、零运费和确定性尾差分配足以覆盖当前学习项目的金额守恒，同时避免引入税务、物流费用和多币种复杂度。

累计退款公式可以保证多次部分退货在全部完成时精确回到明细应付金额。固定金额券、一单一券和简化状态机能够覆盖领取、锁定、支付、取消和过期的主要链路，不需要建设完整营销平台。毛补贴率按支付日固定，不因未来退款回写历史结果，便于 T+1 计算和人工核对；净补贴率作为扩展项保留。

### 验证方法

M2.2 必须把各业务事件时间、审计时间、到达时间、金额组成、优惠分摊、累计退款和优惠券状态映射到可追溯的字段、关系与约束，并执行 DDL 静态检查。M2.3 固定数据至少覆盖跨日下单与支付、迟到到达、重复回调、两位小数尾差、多明细优惠分摊、部分及全部退款、零应付、优惠券锁定/支付/取消/过期、重复使用和补贴率零分母。

M2.5 在真实 MySQL 执行 DDL、seed 和测试，核对毫秒时间、`update_time` 更新、跨日归属、金额与分摊守恒、累计退款上限、优惠券合法迁移、幂等和失败退出。Milestone 5 还需在固定样例和真实计算引擎核对 `P1_METRIC_030` 的分子、分母、精度和零分母结果。文档检查不构成上述运行验证。

### 影响与风险

运费固定为零、不单列税额、不支持多币种或比例券，是 V1 的明确简化，后续不得从当前模型推断这些能力。按支付日计算毛补贴率不会反映后续退款后的净营销成本；若业务需要净口径，必须新增指标决策，不能静默改变 `P1_METRIC_030`。

优惠和退款的比例分摊会引入尾差处理，所有实现必须复用相同确定性顺序。物理字段名称、MySQL 类型、索引和约束位置仍由 M2.2 确定；`M2-DEC-014` 后续已由 `DR-013` 确认，`M2-DEC-015` 仍阻断固定数据规模。

### 回滚方式

若 M2.2 模型、固定样例或 MySQL 验收证明该规则不可用，由用户确认后新增决策替代本记录，并同步更新正式业务设计、项目规格、指标文档、DDL、seed、生成器和测试。不得直接改写本历史决策，也不得只修改 SQL 造成时间、金额或优惠券口径与文档不一致。

## DR-013：M2.2 MySQL 源表、公共物理规范与约束分工

- 状态：`accepted`
- 决策日期：2026-09-10
- 决策人：用户
- 影响范围：OLTP 源模型、候选 DDL、异常验收、M2.2-M2.5
- 替代决策：无；确认 `M2-DEC-014` 并承接 `DR-009` 至 `DR-012` 的业务语义

### 背景

M2.1 已确认身份、会话、商品、交易、时间、金额和优惠券语义。M2.2 在展开逐表字段和候选 DDL 前，需要先固定 MySQL 源表边界、公共物理类型以及数据库与业务写入层的约束分工，否则表数量、状态类型、异常数据入口和跨行规则可能在实现中产生不一致。

`M2-DEC-014` 原计划在进入 M2.3 前确认，但它直接决定 M2.2 候选 DDL 使用哪些数据库约束，因此本次提前完成评审。`M2-DEC-015` 仍保留为固定数据和生成器规模门禁。

### 决策

V1 在 MySQL 数据库 `ecommerce_oltp` 建立 19 张 OLTP 业务源表。用户与流量主题包括 `user_account`、`user_address`、`visitor`、`traffic_channel`、`visit_session`、`login_event`、`page_view_event`；商品主题包括 `brand`、`category`、`spu`、`sku`；交易主题包括 `cart_event`、`sales_order`、`sales_order_item`、`payment_attempt`、`return_order`、`refund_attempt`；营销主题包括 `coupon`、`user_coupon`。

`visit_session` 只固定归属 `visitor`，登录事件同时关联访客、会话和用户。订单保存收货省份与商品归属快照。V1 不创建独立取消表，取消状态、时间和原因保存在 `sales_order`；不创建状态历史表，当前状态、关键事件时间和 `update_time` 保存在对应业务表。`category` 使用父节点和层级表达固定三级结构，`user_coupon` 表示用户领取实例，一个订单最多关联一个实例。

公共物理基线采用数据库 `ecommerce_oltp`、`InnoDB` 和 `utf8mb4`。每张表使用 `BIGINT UNSIGNED AUTO_INCREMENT` 内部主键并保留唯一业务键；金额使用 `DECIMAL(18,2)`，数量使用 `INT UNSIGNED`，业务与审计时间使用 `DATETIME(3)`，币种使用 `CHAR(3)` 且 V1 仅允许 `CNY`。状态使用 `VARCHAR(32)` 加 `CHECK`，不使用 MySQL `ENUM`。可变记录保留 `create_time`、`update_time`，业务事件时间和固定数据审计时间必须显式提供。主数据使用 `is_deleted` 和可空 `deleted_at`，交易与事件表禁止业务硬删除。`request_id` 只要求在对应业务过程内唯一。

MySQL 负责 `PRIMARY KEY`、`UNIQUE`、`NOT NULL`、核心 `FOREIGN KEY`、状态集合及单行金额/数量范围等结构约束；同一订单最多一笔成功支付使用生成列与唯一索引。状态迁移、累计退货与退款上限、优惠券锁定和释放、金额分摊以及重复请求返回原对象等跨行或流程规则由 Python 写入层负责。V1 不使用 Trigger 或 Stored Procedure。

正常 seed 只包含合法数据。违反数据库约束的用例使用独立事务执行，并在预期失败后 `ROLLBACK`；跨行或流程异常由 Python 写入层拒绝并返回非零状态。不得通过关闭外键或修改正式 DDL 注入异常数据。

### 理由

19 张表覆盖五个主题与 30 项正式指标需要的源业务过程，同时不引入库存、履约、商家拆单、税务、状态历史平台等 V1 非目标。保留登录事件和订单快照可以支持登录前后身份语义及历史归属；取消和状态历史不单独建表可以降低实现和人工核对成本。

将结构及单行约束放在 MySQL，可以尽早拒绝业务键重复、引用缺失和非法取值；将跨行与流程规则放在 Python 写入层，可以避免 Trigger 和 Stored Procedure 带来的隐藏逻辑、调试成本和跨系统迁移困难。`VARCHAR` 加 `CHECK` 比 MySQL `ENUM` 更容易与 Hive、Spark、Flink 和 Doris 保持统一。

### 验证方法

M2.2 后续必须为 19 张表补齐逐表字段字典、可空性、业务键长度、完整主外键、查询与增量抽取索引、生成列及约束名称，并生成候选 DDL。静态检查至少核对表数、表名唯一、主键、业务键、状态 `CHECK`、金额/数量类型、软删除字段、`update_time`、成功支付唯一索引和外键拓扑。

M2.3/M2.4 必须分别验证正常 seed 不包含非法数据、数据库约束失败用例在独立事务回滚、Python 写入层对状态迁移和跨行累计规则返回非零状态。M2.5 在 M1 MySQL 门禁通过后，才可在真实 MySQL 执行 DDL、约束失败、同日重跑和 Binlog 相关验收。当前文档检查不能证明 DDL 已实现或 MySQL 已验证。

### 影响与风险

## DR-016：M2.2 正向交易源表字段设计

- 状态：`accepted`
- 决策日期：2026-09-10
- 决策人：用户
- 影响范围：加购、订单、订单明细、金额约束、索引、增量抽取、固定数据、M2.2-M2.5

### 背景

`DR-010` 已确认加购与订单粒度，`DR-011` 已确认订单状态机和删除策略，`DR-012` 已确认时间、金额、优惠分摊及优惠券语义，`DR-013` 已确认 19 张 MySQL 源表和公共物理规范。M2.2 已完成用户、流量和商品字段设计，继续设计支付及逆向交易前，需要先固定 `cart_event`、`sales_order` 和 `sales_order_item` 的字段、商品快照、金额关系、单行约束和索引方向。

### 决策

本批确认三张正向交易源表共 57 个字段：`cart_event` 14 个、`sales_order` 19 个、`sales_order_item` 24 个。三张表均使用 `BIGINT UNSIGNED AUTO_INCREMENT` 内部主键，事件、订单和明细分别使用 `cart_event_id`、`order_no`、`order_item_no` 作为唯一业务键；加购和下单分别使用唯一 `request_id VARCHAR(64)` 作为流程幂等键。

`cart_event` 保存事件时访客、会话、可空用户、SKU、动作类型、前后数量、有效性、无效原因、`action_time` 和 `create_time`。动作只允许 `ADD`、`CHANGE_QUANTITY`、`REMOVE`。有效事件分别要求 0 到正数、两个不同正数、正数到 0；无效事件必须保存原因和原始数量。重复请求由 Python 写入层返回原事件。

`sales_order` 保存用户、地址、可空优惠券领取实例、订单状态、收货省份编码及名称快照、原价/商品优惠/优惠券优惠/应付四项金额、币种、下单及取消时间和审计时间。状态只允许 `CREATED`、`PAID`、`CANCELLED`、`PARTIALLY_REFUNDED`、`REFUNDED`；只有 `CANCELLED` 同时保存取消时间和原因。未使用优惠券时，`user_coupon_pk` 为空且优惠券优惠金额为 `0.00`。

`sales_order_item` 保存订单、SKU、正整数数量，Brand、三级 Category、SPU、SKU 的业务键与名称快照，原始单价及四项明细金额。同一订单内一种 SKU 只允许一条明细，使用 `(order_pk, sku_pk)` 唯一约束。订单和明细金额均使用 `DECIMAL(18,2)`，非负并满足应付金额公式；明细原价等于原始单价乘数量，币种只允许 `CNY`。

所有外键使用 `RESTRICT`。`cart_event` 和 `sales_order_item` 保持 append-only；`sales_order` 保存当前状态并在合法变化时刷新 `update_time`；三张表不使用软删除字段且禁止业务删除。订单头与明细金额合计、优惠分摊、用户与地址/优惠券归属、事件主体与会话一致性、请求重放和状态迁移由 Python 写入层保证，不使用 Trigger 或 Stored Procedure。`sales_order.user_coupon_pk` 的目标为 `user_coupon`，但目标字段与完整外键名称等待营销表字段确认。

查询和增量索引方向为：加购按访客、用户、会话、SKU 与 `action_time` 查询并按 `(create_time, cart_event_pk)` 抽取；订单按用户、状态、优惠券与业务时间查询并按 `(update_time, sales_order_pk)` 抽取；明细按订单/SKU 唯一、按 SKU 查询并按 `(create_time, sales_order_item_pk)` 抽取。索引名和全部约束名随 19 张表候选 DDL 统一确定。

### 理由

将加购保留为带有效性标记的 append-only 事件，可以同时支持正常行为、异常验收和事件时间统计，不需要覆盖错误记录。订单头保存省份与金额汇总，订单明细保存完整商品归属和价格快照，可以稳定支撑按品牌、品类、SPU、省份和订单金额分析，避免商品主数据变化重写历史交易。

MySQL 只承担可表达的结构、唯一、外键、状态集合和单行金额/数量约束，跨行金额守恒、比例分摊、所有权与状态迁移集中到 Python 写入层，与 `DR-013` 的约束分工一致，也避免引入 Trigger 和 Stored Procedure。

### 验证方法

本批先执行静态检查：核对三张表分别为 14、19、24 个字段且无重复；检查业务键、`request_id`、可空性、商品快照、金额类型、动作/状态集合、取消字段组合、append-only/可变表审计字段和索引方向一致。同步确认当前累计 14 张表、153 个字段，且剩余 5 张表没有被经验默认值补全。

## DR-018：M2.2 营销源表字段设计

- 影响范围：优惠券、领取实例、快照、状态组合、订单关联、索引、增量抽取、固定数据、M2.2-M2.5

### 决策

本批确认两张营销源表共 28 个字段：`coupon` 11 个、`user_coupon` 17 个。`coupon` 使用 `coupon_pk BIGINT UNSIGNED` 内部主键和 `coupon_id VARCHAR(32)` 唯一业务键，保存名称、`discount_amount DECIMAL(18,2)`、`minimum_original_amount DECIMAL(18,2)`、`valid_from`、`valid_to`、软删除字段和审计时间。V1 只支持固定金额券；优惠金额必须大于 0，门槛不得为负，有效期结束不得早于开始。

领取实例状态只允许 `CLAIMED`、`LOCKED`、`USED`、`EXPIRED`。初次 `CLAIMED` 的锁定和释放时间为空；取消释放后可以在 `CLAIMED` 保留成对的最近锁定/释放时间。`LOCKED` 必须有 `locked_at` 且释放、使用、过期时间为空；`USED` 必须有 `locked_at`、`used_at` 且释放、过期时间为空；`EXPIRED` 必须有 `expired_at`、`used_at` 为空，可以从未锁定直接过期，也可以在取消释放后过期。重新锁定时更新 `locked_at` 并清空 `released_at`，V1 不增加状态历史表。

关系固定为 `user_coupon.coupon_pk → coupon.coupon_pk`、`user_coupon.user_pk → user_account.user_account_pk`、`sales_order.user_coupon_pk → user_coupon.user_coupon_pk`，全部使用 `RESTRICT`。不在 `user_coupon` 增加 `locked_order_pk`；当前锁定或使用订单通过 `sales_order.user_coupon_pk` 反向查询，避免循环外键。一个领取实例最多关联一个成功支付订单，但可以多次锁定、未支付取消和释放。

`coupon` 是可软删除主数据；软删除后不得新领取，已有领取实例保持原快照和状态。`user_coupon` 是保存当前状态的可更新交易记录，不设置软删除字段并禁止业务硬删除。V1 不增加发行额度、库存、抢券、每用户领取上限或比例折扣券。

查询和增量索引方向固定为：`coupon` 唯一 `coupon_id`，并覆盖 `(valid_from, valid_to, is_deleted, coupon_pk)`、`(update_time, coupon_pk)`；`user_coupon` 唯一 `user_coupon_no`、`request_id`，并覆盖 `(user_pk, coupon_status, valid_to, user_coupon_pk)`、`(coupon_pk, coupon_status, user_coupon_pk)`、`(coupon_status, valid_to, user_coupon_pk)`、`(update_time, user_coupon_pk)`。完整字段字典见正式业务设计 8.8 节，索引与约束名称留到候选 DDL 批次统一确定。

## DR-020：M2.2 Schema 物理规范收口

- 状态：`accepted`
- 决策日期：2026-09-11
- 决策人：用户
- 影响范围：Candidate DDL、Schema 命名台账、生成列、FK 拓扑、静态检查、M2.2
- 替代决策：无

### 背景

T1 已为 19 张 MySQL 源表建立完整物理规范候选，包括命名台账、生成列物理形式、建表顺序和回滚顺序。其验收既需要保证所有可命名约束与索引可追踪，也需要处理 MySQL 的实际 Primary Key 索引名固定为 `PRIMARY`、不能物理命名为 `pk_<table>` 的边界。

### 决策

接受 T1 的完整物理规范：

- 命名台账共 183 项，包括 19 个逻辑 PK、30 个 UQ、42 个 CHECK、32 个 FK 和 60 个非唯一二级索引。`pk_<table>` 仅作为 Schema 设计文档和静态检查中的逻辑标识；Candidate DDL 对每张表使用 MySQL 的 `PRIMARY KEY`，实际 Primary Key 索引名统一为 `PRIMARY`。除该 MySQL 固有限制外，所有 `UNIQUE`、`CHECK`、`FOREIGN KEY` 与非唯一二级索引必须使用 T1 台账中的显式名称，并在 19 张表范围内唯一。
- `payment_attempt.successful_order_pk` 与 `refund_attempt.successful_return_order_pk` 均使用 `VIRTUAL GENERATED ALWAYS`。它们分别配合 `uq_payment_attempt_successful_order` 和 `uq_refund_attempt_successful_return_order`，保持 `DR-017` 已确认的一单最多一笔成功支付、一张退单最多一笔成功退款语义。
- 19 表创建顺序固定为：`user_account` → `visitor` → `traffic_channel` → `brand` → `category` → `coupon` → `user_address` → `visit_session` → `spu` → `sku` → `user_coupon` → `login_event` → `page_view_event` → `cart_event` → `sales_order` → `sales_order_item` → `payment_attempt` → `return_order` → `refund_attempt`。Schema 回滚顺序必须是该顺序的精确反向。
- `category.parent_category_pk → category.category_pk` 是唯一同表自引用，不构成表级创建循环；seed 写入仍须先父级后子级。

本记录承接并解除 `DR-017`、`DR-018` 等既有记录中留待 M2.2 的物理名称、生成列形式与依赖顺序事项，但不改写这些历史记录，也不改变其已确认字段、关系或业务语义。

### 理由

该方案与 MySQL 的实际 Primary Key 行为一致，并为 T2 提供唯一、可追踪且可自动检查的完整物理输入。两个派生键没有独立读取或审计保留需求，采用 `VIRTUAL` 避免冗余聚簇数据，其唯一二级索引仍保存判重键。父表先建、子表先删的固定顺序可以在不关闭外键的前提下创建和回滚隔离测试 Schema。

### 验证方法

T2 生成 Candidate DDL 后静态检查每张表包含一个 `PRIMARY KEY`，并映射到对应的 `pk_<table>` 逻辑标识；检查其余 164 个可命名对象均出现且仅出现一次，两个 `VIRTUAL GENERATED ALWAYS` 表达式与唯一索引成对出现，31 个跨表 FK 的目标表先于子表创建，回滚顺序与创建顺序精确相反。M2.5 在 MySQL 8.0.46 门禁通过后，再通过 `SHOW INDEX`、`information_schema` 和约束行为测试验证实际物理结果。静态检查不能替代 MySQL 运行验证。

### 影响与风险

自动化检查不得把 19 个实际 `PRIMARY` 名称误判为重复；外键继续按表/列引用，不依赖 Primary Key 索引名。当前 `VIRTUAL` 选择和建表顺序尚未在目标 MySQL 执行，证据状态仍是静态设计。若未来迁移数据库、目标版本不支持该实现或迁移工具不能保持顺序，必须新增决策，不得改写本记录。

### 回滚方式

若目标 MySQL 版本或迁移工具证明任一物理选择不可用，由用户确认后新增替代决策，并同步更新 M2.2 业务设计、Candidate DDL 和静态检查。必须保留 `DR-017` 的业务唯一语义，不得伪造或尝试重命名 MySQL 的实际 `PRIMARY` 索引，也不得静默切换 Trigger、Stored Procedure 或取消唯一保护。
