# 项目决策记录

本文件记录会影响项目范围、业务口径、架构、组件版本、数据模型、接口、安全约束或验收方式的正式决策。临时想法和个人学习笔记不在此记录。

## 使用规则

- 决策编号使用连续格式 `DR-001`、`DR-002`。
- 状态只使用 `proposed`、`accepted`、`superseded` 或 `rejected`。
- 未获得必要证据或确认前，状态保持 `proposed`。
- 新决策不得覆盖旧记录；发生变更时新增决策，并在两条记录中互相引用。
- 涉及旧仓库内容迁入时，必须记录来源、采用理由、必要改造、验证方法和回滚方式。
- 静态检查、文件存在或配置草案不得作为运行验证证据。

> 适用性说明：`accepted` 表示决策在其形成时被采用，不保证其全部时点事实仍代表当前实现。旧 19 表、Pilot、候选 DDL 与部署前证据边界由后续连续决策（尤其 `DR-028`、`DR-031`、`DR-034`～`DR-037`）更新；阅读旧记录时必须同时查看其“历史说明／当前适用边界”和后续关联决策，不得仅凭索引状态推断当前工程状态。

## DR-001：DataX 直写 Hive ODS 对应 HDFS 分区

- 状态：`accepted`
- 决策日期：2026-09-04
- 决策人：用户
- 影响范围：离线架构、Milestone 1、3、6、质量与对账
- 替代决策：无

### 背景

原离线架构在 DataX 与 Hive ODS 之间设置独立的 HDFS landing/staging Text/CSV 数据层。用户要求删除该独立层，同时保留 DataX 和以 Hive/HDFS 为核心的离线数仓主线。

### 决策

保留 DataX，并使用 HDFS Writer 直接写入 Hive ODS 发布范围内的 HDFS ORC + Snappy，不建设独立持久化的 Text/CSV 中间数据层。Hive ODS 同时表示 Hive 逻辑表和其 HDFS 物理存储；ODS 装载负责显式分区注册、`business_date`、`extract_time`、`batch_id`、`source_table` 审计字段、幂等发布和失败隔离。根据后续 `DR-037` 的时间语义，当前实现先写 batch staging，再由 Validation / Publish 按每行 `business_date` 原子发布最终 `dt`；该临时发布区不构成独立持久化数据层，也不改变本决策的架构边界。

### 理由

该方案满足删除独立中间层的要求，同时保留 DataX 的批量抽取职责和 Hive ODS 的正式数据分层。未采用 Spark JDBC 替代 DataX，因为这会超出本次架构调整范围；未采用只删除流程图节点但不重定义写入责任的方案，因为它会造成 ODS 所有权、格式和验收边界不清。

### 验证方法

Milestone 1 验证 DataX、HDFS 和 Hive 的候选版本组合及最小写入/读取能力。Milestone 3 使用固定 MySQL 输入验证 HDFS Writer 的 ORC + Snappy 输出、Hive 分区可见性、四个审计字段、源表与 ODS 对账、首次运行、同日重跑、连续回补、异常批次保护和失败时非零退出状态。只有真实验证通过后，该路径才能标记为 `verified`。

### 影响与风险

DataX HDFS Writer 的格式、依赖和文件行为尚未在目标 ECS 环境验证。直接写 ODS 还要求明确批次发布原子性、临时文件处理和失败回滚；这些内容是 Milestone 3 的实现与验收责任，当前决策不构成运行证明。

### 回滚方式

若 Milestone 1 或 3 证明直写方案不可行，保留失败日志、版本、配置和固定输入，新增后续决策记录替代本决策，并经用户评审后调整架构；不得静默恢复旧链路或改用 Spark JDBC。

## DR-002：Agent 答复总结与记录确认门禁

- 状态：`superseded`
- 决策日期：2026-09-04
- 决策人：用户
- 影响范围：协作规则、变更日志、决策治理、Milestone 0
- 替代决策：`DR-030`

### 背景

项目需要在每轮协作结束时明确本轮实际执行的核心操作和形成的核心决策，并由用户控制这些内容是否成为仓库内的正式记录，避免关键变化遗失，也避免把普通讨论自动升级为项目事实。

### 决策

Agent 每次最终答复必须简要总结核心操作和核心决策，并询问用户是否将本轮总结写入 `CHANGELOG.md`、`docs/decision-register.md` 或两者。除用户已在当前请求中明确授权记录的内容外，未获得确认前不得自动写入。确认后，只有可交付变更写入 `CHANGELOG.md`，只有影响范围、业务口径、架构、版本、模型、接口、安全或验收方式的正式决策写入 `docs/decision-register.md`；同时符合两类用途时可以分别记录。

### 理由

该规则让用户保留正式记录的最终控制权，同时通过固定的答复收尾降低遗漏重要变更和决策的风险。按文件职责筛选内容能够避免修改日志退化为对话流水账，也避免决策记录被一般操作淹没。

### 验证方法

静态检查 `AGENTS.md`、`README.md`、`docs/spec.md` 和 `docs/plan.md`，确认两个文件的路径、职责、答复总结要求和用户确认门禁一致。后续每轮协作通过最终答复及用户确认记录抽查该规则是否被遵守；该静态检查不证明未来答复已经执行规则。

### 影响与风险

所有 Agent 答复增加固定的总结与确认步骤。若不按文件职责筛选，可能造成重复记录或无效噪声；若用户未确认却自动写入，则会把尚未采纳的讨论误记为项目事实。

### 回滚方式

若该流程影响协作效率，由用户确认新的收尾或记录方式，新增决策替代本记录，并同步更新 `AGENTS.md`、`README.md`、`docs/spec.md` 和 `docs/plan.md`；不得直接删除历史决策。

### 影响与风险

下一阶段允许开展主机、网络、磁盘、JDK 和组件兼容性验证，但不得把 M0 的文档验收当作安装、启动、连通或链路运行证明。业务模型、指标口径、精确版本和实时细节中的未决事项继续保持原状态。

### 回滚方式

## DR-004：Milestone 2 受限预设计例外

- 状态：`superseded`
- 决策日期：2026-09-04
- 决策人：用户
- 影响范围：阶段门禁、业务模型预设计、Milestone 1-2
- 替代决策：`DR-008`（自 2026-09-09 起替代 M2 保持 `pending` 和仅限预设计的边界）

### 背景

Milestone 1 的进入门禁已经开放，但尚未实际启动。用户希望暂缓 Milestone 1 并先推进 Milestone 2；现行阶段计划则要求 MySQL 先通过 Milestone 1 的启动和连接验证，且禁止在门禁未满足时创建正式业务模型和运行性产物。为在不虚构环境能力、不改变强制顺序的前提下提前收敛业务问题，需要定义一个边界明确的文档预设计例外。

### 决策

Milestone 1、2 均保持 `pending`，允许先创建和维护 Milestone 2 业务设计文档（现路径为 `docs/milestone-2-business-design.md`）。当时的受限设计只整理五个主题的业务过程、概念关系、30 项正式指标的过程依赖、验收场景和 `DECISION_REQUIRED`，不构成正式进入 Milestone 2。

预设计期间不得创建或修改正式 DDL、seed、数据生成器、测试程序、运行脚本、字段类型、状态枚举或可执行接口；`mysql/ddl/`、`mysql/seed/` 和 `mock/` 继续保持占位状态，不创建 `generator/` 或 `tests/`。只有 MySQL 通过 Milestone 1 的启动和连接验证，且 OLTP 表、字段、主外键、状态机和硬删除策略经用户确认后，才能正式进入 Milestone 2。

### 理由

该方案允许在暂时无法或不准备实施基础设施时先完成业务问题梳理，同时保留环境验证、业务确认和正式实现之间的证据边界。未采用直接把 Milestone 2 标记为 `in progress` 的方案，因为其进入条件尚未满足；未采用生成不可执行候选 DDL 的方案，因为候选字段和状态容易被误当成已采用模型，并会绕过必须由用户确认的业务语义。

### 验证方法

静态核对 `AGENTS.md`、`README.md`、`docs/spec.md` 和 `docs/plan.md`：Milestone 1、2 均为 `pending`，预设计允许范围、禁止范围和正式进入条件一致。执行 `git diff --check`；检查 `mysql/ddl/`、`mysql/seed/` 和 `mock/` 没有新增运行性内容，`generator/`、`tests/` 不存在；确认 30 项正式指标、10 项扩展指标、5 项实时候选和六个 Project 2 只读契约范围未改变。上述检查只证明文档和门禁一致，不证明 MySQL 或任何数据模型已经运行。

### 影响与风险

## DR-009：M2 身份、会话与用户分类基础语义

- 状态：`accepted`
- 决策日期：2026-09-09
- 决策人：用户
- 影响范围：用户与流量模型、指标口径、M2.1-M2.4
- 替代决策：无

### 决策

`visitor_id` 与 `user_id` 分离，一个用户允许关联多个 `visitor_id`。登录前事件保留匿名身份且不追溯改写；登录后事件同时记录事件发生时的 `visitor_id` 和 `user_id`；登录动作本身不切断当前会话。

会话在连续 30 分钟无活动后重新开始，并在跨 `Asia/Shanghai` 自然日时强制切分。会话渠道取会话首次进入渠道；会话内渠道变化不拆分会话。

新访客和老访客按 `visitor_id` 首次访问日期是否等于业务日期判断并保持互斥。新增用户按注册日期等于业务日期判断。活跃用户是在业务日期内至少产生一次带 `user_id` 的访问、加购、下单或支付行为的用户。回流用户是此前活跃、连续 7 个完整自然日未活跃并在业务日期再次活跃的用户。新增用户与回流用户互斥，活跃用户集合可以包含两者。

新增下单人数和新增支付成功人数分别按个人首次有效订单日期和首次成功支付日期识别；有效订单与成功支付的具体状态范围继续由 `M2-DEC-006`、`M2-DEC-007` 和 `M2-DEC-009` 决定，本决策不提前补全。

### 理由

身份分离并保留事件发生时的标识能够避免登录后回写历史导致的口径漂移，同时支持一个用户跨设备或重置标识的常见情况。固定 30 分钟超时、自然日切分和首次渠道归属能形成可复现、易人工核对的离线会话规则。将活跃定义限定为可识别用户的实际业务行为，并明确回流观察窗口，可避免仅登录或注册状态造成分类歧义。

该方案不建设复杂身份图谱或跨设备自动合并，符合个人学习项目的实现和维护成本；实时事件的迟到、乱序与状态合并仍留到 Milestone 8 评审。

### 验证方法

M2.3 固定验收数据至少覆盖匿名访问后登录、一个用户关联多个 `visitor_id`、29 分钟与30分钟间隔、跨 `Asia/Shanghai` 零点、会话内渠道变化、新老访客互斥、新增与回流互斥、连续 7 个完整自然日未活跃后回流，以及个人首次有效订单和首次成功支付跨日的场景。M2.4 为相同输入生成确定性结果；M2.5 在真实 MySQL 核对源记录及预期分类。

相关指标只有在各自公式、事件字段和状态范围确认并于真实引擎核对后才能标记为 `verified`。文档一致性或静态测试不构成指标运行证明。

### 影响与风险

跨自然日强制切分会把持续跨零点的访问分成两个会话；会话渠道的首次归属不会反映同一会话中的后续渠道变化。登录前事件不回写意味着用户级分析不会自动吸收其登录前匿名行为。这些都是已接受的 V1 简化边界，后续模型和样例必须保持一致。

有效订单和成功支付状态尚未确认，因此 `P1_METRIC_017`、`018` 只能取得分类框架，不能形成最终公式。页面分类、具体事件字段和实时处理策略也不由本决策确定。

## DR-010：M2 商品层级、加购与订单粒度

- 状态：`accepted`
- 决策日期：2026-09-09
- 决策人：用户
- 影响范围：商品与交易模型、业务键、指标基础、M2.1-M2.4
- 替代决策：无

### 背景

M2.1 需要确定商品层级、加购事件粒度、订单头与订单明细粒度及其幂等边界，才能继续设计支付、退款、金额守恒和 OLTP 物理模型。若 SKU、SPU、Category 和订单明细关系不明确，品牌、品类、SPU 订单指标及固定验收数据无法建立稳定归属。

### 决策

商品层级采用 Brand → SPU → SKU，Category 使用三级结构。一个 SPU 归属一个 Brand 和一个末级 Category，并可以包含多个 SKU；SKU 是商品详情浏览、加购和交易的最小商品单位。订单明细保存下单时的 Brand、Category、SPU 和 SKU 归属快照，商品主数据后续变化不改写历史订单。

一行加购事件表示一个行为主体对一个 SKU 的一次操作，区分新增、修改数量和移除，记录操作前和操作后数量。相同 `request_id` 的重复请求只生效一次；数量必须为非负整数，移除后的数量为 0。加购人数按事件发生时的主体去重：已登录使用 `user_id`，匿名使用 `visitor_id`，不追溯合并登录前行为。

V1 只有注册用户可以下单。一次结算生成一个订单头，一种 SKU 生成一条订单明细；一个订单可以包含多条明细，但不进行仓库、商家或物流拆单。`order_no`、`order_item_no` 分别作为订单头和订单明细业务键；相同下单 `request_id` 的重复提交返回原订单，不创建新订单。订单明细数量必须为正整数。

本决策当时未确定金额组成、有效订单状态、支付成功状态、取消或退款作用范围；其中 `M2-DEC-007` 至 `010` 后续已由 `DR-011` 确认，时间与金额规则仍由 `M2-DEC-011`、`012` 确认。

### 理由

以 SKU 作为最小可交易商品、SPU 作为商品聚合层，能够支持商品详情、加购和订单明细的一致关联。三级 Category 足以展示电商商品层级建模，同时避免为学习项目引入任意深度树的额外实现成本。订单时快照保证商品归属变化后历史指标仍可复现。

加购采用事件粒度可以保留新增、改量、移除和重复请求，便于离线与未来实时链路使用同一业务事实。订单不拆分符合 V1 不建设库存和履约域的范围，`request_id` 幂等与明确业务键可以覆盖重复请求验收而不引入额外服务架构。

### 验证方法

M2.3 固定验收数据至少覆盖一个 Brand 下多个 SPU、一个末级 Category 下多个 SPU、一个 SPU 下多个 SKU、商品归属变化后历史订单快照不变、加购新增/改量/移除、重复加购请求、匿名与登录主体、同一订单多条明细、重复下单请求和非法明细数量。预期结果必须证明业务键唯一、重复 `request_id` 不新增业务结果、订单明细快照稳定以及数量边界符合决策。

M2.5 在真实 MySQL 执行相关 DDL、seed 和测试后，核对约束、幂等输入、查询结果和失败退出。静态文档与候选 DDL 检查不构成运行验证。

### 影响与风险

V1 不支持游客下单，也不表达仓库、商家或物流拆单；这些能力不得从现有模型中推断。订单快照会产生一定字段冗余，但用于换取历史归属稳定。按事件时主体统计加购人数可能把同一自然人在登录前后计为两个主体，这是与 `DR-009` 不追溯合并边界一致的已知限制。

Category 固定三级会限制任意深度分类；若后续真实需求变化，不能仅修改表结构而不重新评审指标归属和固定样例。

### 回滚方式

## DR-011：M2 支付、逆向交易、状态机与删除策略

- 状态：`accepted`
- 决策日期：2026-09-09
- 决策人：用户
- 影响范围：交易模型、状态枚举、增量抽取、指标基础、M2.1-M2.5
- 替代决策：无

### 背景

M2.1 已确认订单头、订单明细和请求幂等，但支付尝试、取消、退单、退款、状态迁移及删除策略仍会直接影响源模型、金额守恒、DataX 增量完整性和退单指标。需要先固定这些业务边界，再设计物理约束和验收数据。

### 决策

一个订单允许多次支付尝试但最多一次成功，V1 不支持分次支付；成功支付金额必须等于订单应付金额。每次尝试使用独立 `payment_no`，相同 `request_id` 只创建一次。重复支付回调不得重复记成功或修改首次成功时间。支付成功人数按 `paid_at` 所属业务日期对 `user_id` 去重。

只有未支付的 `CREATED` 订单可以取消。支付成功后不能取消，只能进入退单和退款流程。退单业务单与资金退款分离；一条退单作用于一条订单明细，支持部分数量和多次退单，累计数量不得超过购买数量。退款关联退单、原订单和原成功支付，支持多次部分退款，累计成功金额不得超过成功支付金额。退单数以 `COMPLETED` 退单业务单为基础，商品归属使用原订单明细快照。

订单状态为 `CREATED`、`PAID`、`CANCELLED`、`PARTIALLY_REFUNDED`、`REFUNDED`；支付尝试和退款尝试状态为 `CREATED`、`SUCCESS`、`FAILED`；退单状态为 `APPLIED`、`APPROVED`、`REJECTED`、`COMPLETED`。`CANCELLED`、`REFUNDED` 是订单终态。退单只有在关联退款成功后才能进入 `COMPLETED`。支付或退款失败后若需重试，必须创建新的业务尝试记录。非法迁移必须拒绝且不修改原记录，合法状态变化必须更新 `update_time`。

用户、商品、订单、支付、退单、退款和优惠券禁止业务硬删除。主数据使用停用或软删除，交易数据保留原记录；加购事件保持 append-only，错误事件通过有效性标记处理。停用或软删除必须更新 `update_time`。V1 不建设周期性全量快照识别硬删除；固定测试数据只允许在隔离测试库整体重建。

金额组成、精度与舍入继续由 `M2-DEC-012` 确认，事件时间和跨日归属由 `M2-DEC-011` 确认，优惠券状态机由 `M2-DEC-013` 确认。

### 理由

多次尝试、最多一次成功的支付模型能够覆盖失败重试和重复回调，同时避免分次支付带来的额外金额分摊复杂度。把退单业务和退款资金分开，可以独立表达申请处理与资金结果，并支持部分、多次逆向交易和可解释的数量、金额守恒。

明确状态机和非法迁移行为有利于固定异常样例和后续数据库约束。禁止业务硬删除并让软删除更新 `update_time`，可以让基于更新时间的 DataX 增量捕获删除语义，避免为 V1 增加周期性全量快照和删除对账成本。

### 验证方法

M2.3 固定验收数据至少覆盖支付失败后新尝试成功、同单第二笔成功被拒绝、重复回调不改变首次成功时间、未支付取消、已支付取消被拒绝、单明细部分和多次退单、超数量退单、部分和多次退款、累计退款超限、无成功支付退款、非法状态迁移、终态后变更、软删除或停用更新 `update_time`，以及交易数据未被业务硬删除。

M2.5 在真实 MySQL 执行相关 DDL、seed 和测试，核对唯一性、引用、状态、累计数量与金额、幂等结果、`update_time` 和失败退出。静态文档、DDL 语法或候选测试不构成 MySQL 运行验证。

### 影响与风险

V1 不支持分次支付、支付后直接取消、游客下单或业务硬删除。支付或退款失败重试会产生新的尝试记录，后续指标和对账必须区分业务单与尝试流水。退单完成依赖退款成功，因此没有成功退款的已批准退单不会计入完成退单数。

禁止硬删除不能替代隐私合规的数据擦除方案；本项目只使用合成数据，若未来引入真实个人数据，必须新增安全与数据生命周期决策。金额字段、应付金额和退款金额精度仍未确认，当前累计上限只是业务约束，不是已实现数据库校验。

### 回滚方式

若物理模型、固定样例或 MySQL 验收证明这些规则不可行，由用户确认后新增决策替代本记录，并同步更新 M2 业务设计、项目规格、指标说明、DDL、seed、生成器和测试。不得直接改写历史状态机、用硬删除绕过增量设计或删除已有运行证据。

## DR-012：M2 时间、金额与优惠券语义

- 状态：`accepted`
- 决策日期：2026-09-09
- 决策人：用户
- 影响范围：时间与金额模型、优惠券状态机、`P1_METRIC_030`、M2.1-M2.5
- 替代决策：无；承接 `DR-011` 保留的时间、金额与优惠券待决策项

### 背景

`DR-009` 至 `DR-011` 已确认身份、会话、商品、正向与逆向交易、状态机和删除边界，但各过程的事件时间、跨日归属、金额精度、优惠分摊、累计退款以及优惠券状态仍未形成结论。这些语义直接阻断 M2.2 的字段、关系与约束设计，也使 `P1_METRIC_030` 缺少可实现的基础公式。

### 决策

所有业务时间统一按 `Asia/Shanghai` 解释并保留毫秒精度，具体 MySQL 类型留到 M2.2。业务日期必须由对应事件时间计算：页面访问使用 `event_time`，加购使用 `action_time`，订单使用 `ordered_at`，支付使用首次成功的 `paid_at`，取消使用 `cancelled_at`，退单完成使用 `completed_at`，成功退款使用 `refunded_at`，用户注册使用 `registered_at`。跨日过程分别归属各自事件日期；记录创建和更新时间只用于审计及增量抽取，不替代指标业务时间。数据到达时间与事件时间分开保存，迟到数据仍按事件时间归属。

V1 只支持人民币 `CNY`，金额保留两位小数并使用 `HALF_UP`。商品价格含税，不单列税额，运费固定为 `0.00`。数量为正整数，金额、优惠和退款不得为负。订单应付金额等于明细原价金额之和减去商品优惠和优惠券优惠，优惠不得超过订单原价；违反时拒绝创建订单。订单级商品优惠和优惠券优惠分别按明细原价比例分摊，舍入尾差按明细原价金额降序、`order_item_no` 升序分配，保证明细与订单金额守恒。成功支付金额必须等于订单应付金额。

部分退货使用累计法计算退款：累计可退金额为 `ROUND(明细应付金额 × 累计完成退货数量 ÷ 购买数量, 2)`，本次退款为累计可退金额减去此前成功退款金额。累计完成退货数量和累计成功退款金额不得超过购买数量和明细应付金额；全部商品完成退款后，累计成功退款金额必须等于订单应付金额。

V1 只支持可设置最低订单原价门槛的固定金额优惠券。只有注册用户可以领取和使用，一个订单最多一张券，一个领取实例最多成功使用一次。领取实例状态为 `CLAIMED`、`LOCKED`、`USED`、`EXPIRED`，允许 `CLAIMED → LOCKED → USED`、`CLAIMED → EXPIRED`；未支付订单取消后，未过期时 `LOCKED → CLAIMED`，已过期时 `LOCKED → EXPIRED`。有效期在锁券时检查，合法锁定后不因支付时间超过有效期而失效；支付成功后不因退单或退款返还。

`P1_METRIC_030` 定义为按首次成功支付 `paid_at` 业务日期统计的优惠券毛补贴率。分子为当日成功支付订单的优惠券优惠金额之和，分母为同一批订单的商品原价金额之和；后续退款不追溯修改。分母为零时输出 `0`，比率保留 4 位小数，百分比展示保留 2 位小数，使用 `HALF_UP`。净补贴率不纳入 V1。

### 理由

以业务事件时间而不是任务时间归属，可以稳定支持跨日、迟到和后续回补；统一业务时区与毫秒精度也便于对支付回调和状态变化排序。CNY 两位小数、含税价格、零运费和确定性尾差分配足以覆盖当前学习项目的金额守恒，同时避免引入税务、物流费用和多币种复杂度。

累计退款公式可以保证多次部分退货在全部完成时精确回到明细应付金额。固定金额券、一单一券和简化状态机能够覆盖领取、锁定、支付、取消和过期的主要链路，不需要建设完整营销平台。毛补贴率按支付日固定，不因未来退款回写历史结果，便于 T+1 计算和人工核对；净补贴率作为扩展项保留。

### 验证方法

M2.2 必须把各业务事件时间、审计时间、到达时间、金额组成、优惠分摊、累计退款和优惠券状态映射到可追溯的字段、关系与约束，并执行 DDL 静态检查。M2.3 固定数据至少覆盖跨日下单与支付、迟到到达、重复回调、两位小数尾差、多明细优惠分摊、部分及全部退款、零应付、优惠券锁定/支付/取消/过期、重复使用和补贴率零分母。

M2.5 在真实 MySQL 执行 DDL、seed 和测试，核对毫秒时间、`update_time` 更新、跨日归属、金额与分摊守恒、累计退款上限、优惠券合法迁移、幂等和失败退出。Milestone 5 还需在固定样例和真实计算引擎核对 `P1_METRIC_030` 的分子、分母、精度和零分母结果。文档检查不构成上述运行验证。

### 影响与风险

运费固定为零、不单列税额、不支持多币种或比例券，是 V1 的明确简化，后续不得从当前模型推断这些能力。按支付日计算毛补贴率不会反映后续退款后的净营销成本；若业务需要净口径，必须新增指标决策，不能静默改变 `P1_METRIC_030`。

优惠和退款的比例分摊会引入尾差处理，所有实现必须复用相同确定性顺序。物理字段名称、MySQL 类型、索引和约束位置仍由 M2.2 确定；`M2-DEC-014` 后续已由 `DR-013` 确认，`M2-DEC-015` 仍阻断固定数据规模。

### 回滚方式

若 M2.2 模型、固定样例或 MySQL 验收证明该规则不可用，由用户确认后新增决策替代本记录，并同步更新正式业务设计、项目规格、指标文档、DDL、seed、生成器和测试。不得直接改写本历史决策，也不得只修改 SQL 造成时间、金额或优惠券口径与文档不一致。

## DR-013：M2.2 MySQL 源表、公共物理规范与约束分工

- 状态：`accepted`
- 决策日期：2026-09-10

- 替代决策：无；确认 `M2-DEC-014` 并承接 `DR-009` 至 `DR-012` 的业务语义

### 背景

M2.1 已确认身份、会话、商品、交易、时间、金额和优惠券语义。M2.2 在展开逐表字段和候选 DDL 前，需要先固定 MySQL 源表边界、公共物理类型以及数据库与业务写入层的约束分工，否则表数量、状态类型、异常数据入口和跨行规则可能在实现中产生不一致。

`M2-DEC-014` 原计划在进入 M2.3 前确认，但它直接决定 M2.2 候选 DDL 使用哪些数据库约束，因此本次提前完成评审。`M2-DEC-015` 仍保留为固定数据和生成器规模门禁。

### 决策

V1 在 MySQL 数据库 `ecommerce_oltp` 建立 19 张 OLTP 业务源表。用户与流量主题包括 `user_account`、`user_address`、`visitor`、`traffic_channel`、`visit_session`、`login_event`、`page_view_event`；商品主题包括 `brand`、`category`、`spu`、`sku`；交易主题包括 `cart_event`、`sales_order`、`sales_order_item`、`payment_attempt`、`return_order`、`refund_attempt`；营销主题包括 `coupon`、`user_coupon`。

`visit_session` 只固定归属 `visitor`，登录事件同时关联访客、会话和用户。订单保存收货省份与商品归属快照。V1 不创建独立取消表，取消状态、时间和原因保存在 `sales_order`；不创建状态历史表，当前状态、关键事件时间和 `update_time` 保存在对应业务表。`category` 使用父节点和层级表达固定三级结构，`user_coupon` 表示用户领取实例，一个订单最多关联一个实例。

公共物理基线采用数据库 `ecommerce_oltp`、`InnoDB` 和 `utf8mb4`。每张表使用 `BIGINT UNSIGNED AUTO_INCREMENT` 内部主键并保留唯一业务键；金额使用 `DECIMAL(18,2)`，数量使用 `INT UNSIGNED`，业务与审计时间使用 `DATETIME(3)`，币种使用 `CHAR(3)` 且 V1 仅允许 `CNY`。状态使用 `VARCHAR(32)` 加 `CHECK`，不使用 MySQL `ENUM`。可变记录保留 `create_time`、`update_time`，业务事件时间和固定数据审计时间必须显式提供。主数据使用 `is_deleted` 和可空 `deleted_at`，交易与事件表禁止业务硬删除。`request_id` 只要求在对应业务过程内唯一。

MySQL 负责 `PRIMARY KEY`、`UNIQUE`、`NOT NULL`、核心 `FOREIGN KEY`、状态集合及单行金额/数量范围等结构约束；同一订单最多一笔成功支付使用生成列与唯一索引。状态迁移、累计退货与退款上限、优惠券锁定和释放、金额分摊以及重复请求返回原对象等跨行或流程规则由 Python 写入层负责。V1 不使用 Trigger 或 Stored Procedure。

正常 seed 只包含合法数据。违反数据库约束的用例使用独立事务执行，并在预期失败后 `ROLLBACK`；跨行或流程异常由 Python 写入层拒绝并返回非零状态。不得通过关闭外键或修改正式 DDL 注入异常数据。

### 理由

19 张表覆盖五个主题与 30 项正式指标需要的源业务过程，同时不引入库存、履约、商家拆单、税务、状态历史平台等 V1 非目标。保留登录事件和订单快照可以支持登录前后身份语义及历史归属；取消和状态历史不单独建表可以降低实现和人工核对成本。

将结构及单行约束放在 MySQL，可以尽早拒绝业务键重复、引用缺失和非法取值；将跨行与流程规则放在 Python 写入层，可以避免 Trigger 和 Stored Procedure 带来的隐藏逻辑、调试成本和跨系统迁移困难。`VARCHAR` 加 `CHECK` 比 MySQL `ENUM` 更容易与 Hive、Spark、Flink 和 Doris 保持统一。

### 验证方法

M2.2 后续必须为 19 张表补齐逐表字段字典、可空性、业务键长度、完整主外键、查询与增量抽取索引、生成列及约束名称，并生成候选 DDL。静态检查至少核对表数、表名唯一、主键、业务键、状态 `CHECK`、金额/数量类型、软删除字段、`update_time`、成功支付唯一索引和外键拓扑。

M2.3/M2.4 必须分别验证正常 seed 不包含非法数据、数据库约束失败用例在独立事务回滚、Python 写入层对状态迁移和跨行累计规则返回非零状态。M2.5 在 M1 MySQL 门禁通过后，才可在真实 MySQL 执行 DDL、约束失败、同日重跑和 Binlog 相关验收。当前文档检查不能证明 DDL 已实现或 MySQL 已验证。

### 影响与风险

该决策使 M2.2 后续设计以 19 张源表为固定边界。逐表字段、字符串长度、完整索引和候选 DDL 尚未完成，当前不能按表清单推断这些产物已经存在。没有 Trigger 或 Stored Procedure 意味着跨行规则的可靠性依赖 Python 写入层及其测试；绕过写入层直接执行 SQL 时，MySQL 只能保证已声明的结构和单行约束。

生成列唯一索引需要在候选 MySQL 8.0.46 上完成语法与行为验证。当前 MySQL 版本仍是候选，文档采用该机制不构成兼容性或运行证明。`M2-DEC-015` 仍未确认，因此不能确定 seed 行数、业务日期跨度或 generator 默认规模。

## DR-014：M2.2 用户与流量源表字段设计

### 背景

`DR-009` 已确认身份、会话和用户分类语义，`DR-013` 已确认 19 张 MySQL 源表、公共物理规范和约束分工。M2.2 继续生成候选 DDL 前，需要先固定依赖最上游的用户与流量 7 张表的字段、可空性、外键、单行约束和索引方向，否则商品浏览、加购、订单和后续 ODS 无法引用稳定的身份及会话结构。

### 决策

本批确认 `user_account`、`user_address`、`visitor`、`traffic_channel`、`visit_session`、`login_event` 和 `page_view_event` 的字段模型。内部主键使用 `<table>_pk` 的 `BIGINT UNSIGNED AUTO_INCREMENT`；`user_id`、`address_id`、`visitor_id`、`channel_code`、`session_id`、`login_event_id` 和 `page_view_id` 使用 `VARCHAR(32)` 并在各自表内唯一。子表通过 `*_pk` 引用内部主键，不冗余复制主表业务键。

`user_account` 保存注册业务时间；`user_address` 保存用户、省市编码与名称和合成详细地址；`visitor` 保存首次及最近访问时间；`traffic_channel` 保存渠道编码和名称。上述四张主数据表保留 `create_time`、`update_time`、`is_deleted` 和可空 `deleted_at`，不保存手机号、IP、设备或浏览器等当前业务和指标不需要的信息。

`visit_session` 归属一个访客和一个首次渠道，保存 `started_at`、`last_event_at`、可空 `ended_at`、`create_time` 和 `update_time`，不固定归属用户。未知或直接访问通过 `channel_code = 'DIRECT'` 的固定渠道记录表达，不使用空渠道。

`login_event` 只记录成功登录，关联事件发生时的访客、会话和用户并保存 `login_at`；`page_view_event` 关联访客、会话、事件渠道和可空用户，保存 `page_type`、`page_path`、可空 `sku_pk`、`event_time`。页面类型只允许 `HOME`、`PRODUCT_DETAIL`、`OTHER`；商品详情页必须关联 SKU，其他页面不得关联 SKU。两张事件表保持 append-only，只保留 `create_time` 到达审计时间。

所有外键采用 `RESTRICT`，不使用级联删除。MySQL 检查业务键唯一、软删除字段一致性、首末事件时间顺序、会话时间顺序以及页面类型与 SKU 可空性；Python 写入层负责 30 分钟无活动与跨自然日切分、会话首渠道、登录不切断会话、登录前事件不回写、访客与会话归属一致以及首末访问时间维护。

查询索引覆盖注册时间、首次访问、访客会话、渠道会话、用户登录、页面访问主体、渠道、页面类型、SKU 和事件时间。可变表使用 `(update_time, <table>_pk)` 作为增量抽取方向，append-only 事件使用 `(create_time, <table>_pk)`；具体索引名、外键名和 `CHECK` 名随 19 张表候选 DDL 统一确定。

### 理由

先确认最上游 7 张表可以为商品浏览、加购、订单和营销模型提供稳定的用户、访客、会话和渠道引用。内部主键与业务键分离便于数据库关联和跨层保留稳定业务标识；不在事件表重复存放业务键可减少同一身份的多份可变表示。

页面类型使用小而明确的三值集合即可支持首页、商品详情页和其余页面的当前指标。使用 `DIRECT` 字典行代替空渠道可以让渠道聚合和外键完整性保持一致。只保存当前业务过程和指标所需字段，避免为个人求职项目引入无实际用途的设备指纹、个人信息和复杂账户体系。

### 验证方法

本批首先执行静态检查：核对 7 张表均有内部主键和唯一业务键，字段名称和 MySQL 类型唯一，四张软删除主数据表具有一致审计字段，两张 append-only 事件表没有 `update_time`，全部外键目标存在，页面类型与 SKU 条件一致，查询和增量索引覆盖已确认业务过程。

候选 DDL 形成后必须通过 SQL 静态检查。M2.5 只能在 M1 MySQL 门禁通过后执行真实验收，至少覆盖业务键重复、外键缺失、软删除组合非法、首末时间倒置、商品详情页缺失 SKU、非商品页错误携带 SKU、匿名与登录后页面访问、登录不切会话、29/30 分钟边界、跨自然日切分、同日重跑和增量抽取。当前文档检查不证明这些运行行为已通过。

### 影响与风险

商品表设计必须提供 `sku.sku_pk`，以完成 `page_view_event.sku_pk` 的正式外键。交易表后续使用同一 `user_pk`、`visitor_pk` 和 `session_pk` 关系。事件表只引用内部主键意味着独立分析源事件时需要连接主表取得业务键，但能避免重复存储和不一致；后续 ODS 是否同时展开业务键留到 M3 设计，不在本决策确定。

### 背景

`DR-010` 已确认 Brand → SPU → SKU、三级 Category、SKU 最小交易粒度和订单快照语义，`DR-013` 已确认四张商品源表，`DR-014` 的 `page_view_event.sku_pk` 还需要稳定的 SKU 外键目标。M2.2 继续设计交易表前，需要固定商品字段、层级关系、价格和增量索引方向。

本记录编号 `DR-015` 属于项目决策记录的连续编号，与业务设计中仍为 `DECISION_REQUIRED` 的验收数据规模决策 `M2-DEC-015` 不同；本记录不确认 seed 数量、日期跨度或生成器规模。

### 决策

本批确认 `brand`、`category`、`spu` 和 `sku` 的 35 个字段。四张表均使用 `<table>_pk` 的 `BIGINT UNSIGNED AUTO_INCREMENT` 内部主键和 `VARCHAR(32)` 唯一业务键，并保留 `create_time`、`update_time`、`is_deleted` 和可空 `deleted_at`。

`brand` 保存 `brand_id` 和 `brand_name VARCHAR(128)`。`category` 保存 `category_id`、`category_name VARCHAR(128)`、可空 `parent_category_pk` 和 `category_level TINYINT UNSIGNED`；Level 1 的父节点为空，Level 2、3 必须存在父节点。`spu` 保存 `spu_id`、`spu_name VARCHAR(255)`、`brand_pk` 和 `category_pk`。`sku` 保存 `sku_id`、`sku_name VARCHAR(255)`、`spu_pk`、`sale_price DECIMAL(18,2)` 和 `currency CHAR(3)`。

关系固定为 `category.parent_category_pk → category.category_pk`、`spu.brand_pk → brand.brand_pk`、`spu.category_pk → category.category_pk`、`sku.spu_pk → spu.spu_pk` 和 `page_view_event.sku_pk → sku.sku_pk`。所有外键使用 `RESTRICT`，不设置级联删除。

MySQL 检查业务键唯一、软删除字段组合、`category_level IN (1, 2, 3)`、层级与父节点的空值组合、`sale_price >= 0` 和 `currency = 'CNY'`。父 Category 必须比子节点低一级、Category 不得形成循环、SPU 只能引用 Level 3 Category 等跨行规则由 Python 写入层负责，不使用 Trigger 或 Stored Procedure。

查询索引方向为 `category(parent_category_pk, category_level, is_deleted, category_pk)`、`spu(brand_pk, is_deleted, spu_pk)`、`spu(category_pk, is_deleted, spu_pk)`、`sku(spu_pk, is_deleted, sku_pk)`；四张表均使用 `(update_time, <table>_pk)` 支持增量抽取。索引名、外键名和 `CHECK` 名随 19 张表候选 DDL 统一确定。

### 理由

该模型直接覆盖 Brand、Category、SPU 和 SKU 四层分析归属，并为商品详情浏览、加购和订单明细提供稳定 SKU 引用。价格保留在 SKU 当前主数据中，订单另存快照，可以同时表达商品价格变化和历史交易不回写。

将层级限定为三级并把复杂跨行检查放在 Python 写入层，可以保持 MySQL DDL 清晰，避免 Trigger 和递归数据库逻辑。当前指标不需要库存、商品规格搜索或媒体资源，省略这些字段可降低数据生成、测试和后续 ODS 建模成本。

### 验证方法

本批首先执行静态检查：核对四张表共 35 个字段且无重复，均具有内部主键、唯一业务键、软删除和审计字段；检查 Category 自关联、SPU 的 Brand/Category 外键、SKU 的 SPU 外键及页面访问的 SKU 外键目标完整；检查价格、币种、层级和索引方向与已确认业务语义一致。

候选 DDL 形成后必须通过 SQL 静态检查。M2.5 只能在 M1 MySQL 门禁通过后执行真实验收，至少覆盖三级 Category 正常树、Level 1 错误携带父节点、Level 2/3 缺失父节点、跨级父子、Category 循环、SPU 引用非末级 Category、SKU 负价格、非 CNY、外键缺失、业务键重复、软删除组合非法、商品归属和价格更新后的 `update_time` 以及历史订单快照不变。当前文档检查不证明这些运行行为已通过。

### 影响与风险

交易表后续可以引用稳定的 `sku_pk`，并在订单明细保存商品归属和价格快照。商品表只保存当前状态，因此不能单独回答历史任意时点的商品属性；是否在数仓 DIM 使用 SCD 仍是后续维度历史策略决策，不由本记录提前确定。

Category 跨行层级和无环约束依赖 Python 写入层，绕过该入口直接写 MySQL 时，数据库只能保证外键存在和本行层级/空值组合。索引方向尚未经过实际数据量和 `EXPLAIN` 验证，运行验收后可能需要调整，但不能在没有证据时声称性能优化有效。

### 回滚方式

## DR-016：M2.2 正向交易源表字段设计

- 状态：`accepted`

- 决策人：用户
- 影响范围：加购、订单、订单明细、金额约束、索引、增量抽取、固定数据、M2.2-M2.5
- 替代决策：无；细化 `DR-010` 至 `DR-013` 的正向交易物理模型

### 背景

- 影响范围：优惠券、领取实例、快照、状态组合、订单关联、索引、增量抽取、固定数据、M2.2-M2.5

### 决策

本批确认两张营销源表共 28 个字段：`coupon` 11 个、`user_coupon` 17 个。`coupon` 使用 `coupon_pk BIGINT UNSIGNED` 内部主键和 `coupon_id VARCHAR(32)` 唯一业务键，保存名称、`discount_amount DECIMAL(18,2)`、`minimum_original_amount DECIMAL(18,2)`、`valid_from`、`valid_to`、软删除字段和审计时间。V1 只支持固定金额券；优惠金额必须大于 0，门槛不得为负，有效期结束不得早于开始。

领取实例状态只允许 `CLAIMED`、`LOCKED`、`USED`、`EXPIRED`。初次 `CLAIMED` 的锁定和释放时间为空；取消释放后可以在 `CLAIMED` 保留成对的最近锁定/释放时间。`LOCKED` 必须有 `locked_at` 且释放、使用、过期时间为空；`USED` 必须有 `locked_at`、`used_at` 且释放、过期时间为空；`EXPIRED` 必须有 `expired_at`、`used_at` 为空，可以从未锁定直接过期，也可以在取消释放后过期。重新锁定时更新 `locked_at` 并清空 `released_at`，V1 不增加状态历史表。

关系固定为 `user_coupon.coupon_pk → coupon.coupon_pk`、`user_coupon.user_pk → user_account.user_account_pk`、`sales_order.user_coupon_pk → user_coupon.user_coupon_pk`，全部使用 `RESTRICT`。不在 `user_coupon` 增加 `locked_order_pk`；当前锁定或使用订单通过 `sales_order.user_coupon_pk` 反向查询，避免循环外键。一个领取实例最多关联一个成功支付订单，但可以多次锁定、未支付取消和释放。

`coupon` 是可软删除主数据；软删除后不得新领取，已有领取实例保持原快照和状态。`user_coupon` 是保存当前状态的可更新交易记录，不设置软删除字段并禁止业务硬删除。V1 不增加发行额度、库存、抢券、每用户领取上限或比例折扣券。

查询和增量索引方向固定为：`coupon` 唯一 `coupon_id`，并覆盖 `(valid_from, valid_to, is_deleted, coupon_pk)`、`(update_time, coupon_pk)`；`user_coupon` 唯一 `user_coupon_no`、`request_id`，并覆盖 `(user_pk, coupon_status, valid_to, user_coupon_pk)`、`(coupon_pk, coupon_status, user_coupon_pk)`、`(coupon_status, valid_to, user_coupon_pk)`、`(update_time, user_coupon_pk)`。完整字段字典见正式业务设计 8.8 节，索引与约束名称留到候选 DDL 批次统一确定。

### 理由

领取时保存金额、门槛和有效期快照，可以让历史订单和补贴指标不受优惠券定义后续变化影响。允许同一用户持有多个独立实例，符合“领取实例一次成功使用”的粒度，也避免用定义与用户的组合键错误合并多次领取。

## DR-020：M2.2 Schema 物理规范收口

- 状态：`accepted`
- 决策日期：2026-09-11
- 决策人：用户
- 影响范围：Candidate DDL、Schema 命名台账、生成列、FK 拓扑、静态检查、M2.2
- 替代决策：无

### 背景

T1 已为 19 张 MySQL 源表建立完整物理规范候选，包括命名台账、生成列物理形式、建表顺序和回滚顺序。其验收既需要保证所有可命名约束与索引可追踪，也需要处理 MySQL 的实际 Primary Key 索引名固定为 `PRIMARY`、不能物理命名为 `pk_<table>` 的边界。

### 决策

接受 T1 的完整物理规范：

- 命名台账共 183 项，包括 19 个逻辑 PK、30 个 UQ、42 个 CHECK、32 个 FK 和 60 个非唯一二级索引。`pk_<table>` 仅作为 Schema 设计文档和静态检查中的逻辑标识；Candidate DDL 对每张表使用 MySQL 的 `PRIMARY KEY`，实际 Primary Key 索引名统一为 `PRIMARY`。除该 MySQL 固有限制外，所有 `UNIQUE`、`CHECK`、`FOREIGN KEY` 与非唯一二级索引必须使用 T1 台账中的显式名称，并在 19 张表范围内唯一。
- `payment_attempt.successful_order_pk` 与 `refund_attempt.successful_return_order_pk` 均使用 `VIRTUAL GENERATED ALWAYS`。它们分别配合 `uq_payment_attempt_successful_order` 和 `uq_refund_attempt_successful_return_order`，保持 `DR-017` 已确认的一单最多一笔成功支付、一张退单最多一笔成功退款语义。
- 19 表创建顺序固定为：`user_account` → `visitor` → `traffic_channel` → `brand` → `category` → `coupon` → `user_address` → `visit_session` → `spu` → `sku` → `user_coupon` → `login_event` → `page_view_event` → `cart_event` → `sales_order` → `sales_order_item` → `payment_attempt` → `return_order` → `refund_attempt`。Schema 回滚顺序必须是该顺序的精确反向。
- `category.parent_category_pk → category.category_pk` 是唯一同表自引用，不构成表级创建循环；seed 写入仍须先父级后子级。

本记录承接并解除 `DR-017`、`DR-018` 等既有记录中留待 M2.2 的物理名称、生成列形式与依赖顺序事项，但不改写这些历史记录，也不改变其已确认字段、关系或业务语义。

### 理由

该方案与 MySQL 的实际 Primary Key 行为一致，并为 T2 提供唯一、可追踪且可自动检查的完整物理输入。两个派生键没有独立读取或审计保留需求，采用 `VIRTUAL` 避免冗余聚簇数据，其唯一二级索引仍保存判重键。父表先建、子表先删的固定顺序可以在不关闭外键的前提下创建和回滚隔离测试 Schema。

### 验证方法

T2 生成 Candidate DDL 后静态检查每张表包含一个 `PRIMARY KEY`，并映射到对应的 `pk_<table>` 逻辑标识；检查其余 164 个可命名对象均出现且仅出现一次，两个 `VIRTUAL GENERATED ALWAYS` 表达式与唯一索引成对出现，31 个跨表 FK 的目标表先于子表创建，回滚顺序与创建顺序精确相反。M2.5 在 MySQL 8.0.46 门禁通过后，再通过 `SHOW INDEX`、`information_schema` 和约束行为测试验证实际物理结果。静态检查不能替代 MySQL 运行验证。

### 影响与风险

自动化检查不得把 19 个实际 `PRIMARY` 名称误判为重复；外键继续按表/列引用，不依赖 Primary Key 索引名。当前 `VIRTUAL` 选择和建表顺序尚未在目标 MySQL 执行，证据状态仍是静态设计。若未来迁移数据库、目标版本不支持该实现或迁移工具不能保持顺序，必须新增决策，不得改写本记录。

### 回滚方式

若目标 MySQL 版本或迁移工具证明任一物理选择不可用，由用户确认后新增替代决策，并同步更新 M2.2 业务设计、Candidate DDL 和静态检查。必须保留 `DR-017` 的业务唯一语义，不得伪造或尝试重命名 MySQL 的实际 `PRIMARY` 索引，也不得静默切换 Trigger、Stored Procedure 或取消唯一保护。

## DR-025：M1 组件验收共享 Evidence Contract

> 当前适用边界：Public API、Secret 去敏、Cleanup Guard 和失败语义继续有效；关于五组件仍为 `candidate` 及必须具备完整目录才能改变状态的结论已由 `DR-026` 替代。

- 状态：`accepted`
- 决策日期：2026-09-14
- 决策人：用户
- 影响范围：M1 验收接口、证据模型、Secret 安全、Cleanup、M1-CAS-02～07
- 替代决策：无；细化 `DR-007` 与 `DR-022` 的组件级证据执行方式

### 背景

MySQL、Hive、Kafka KRaft、Spark on YARN 和 DataX 需要分别生成可回传、可审查且不会相互覆盖的运行证据。如果每个入口复制路径、状态、去敏和 Cleanup 逻辑，五份实现容易漂移，并可能把本地静态检查或不完整摘要误报为组件 Runtime 通过。

### 决策

M1 采用“五个独立组件入口 + 一个最小共享 Evidence Library”的结构。`scripts/m1/lib/evidence-common.sh` 统一负责组件与 `run-id` 校验、绝对输出根和全新私有运行目录、`umask 077`、步骤日志、断言、SHA-256、Secret 去敏、`summary.env` 状态以及临时对象 Cleanup Guard；组件命令、服务生命周期、固定输入和结果断言保留在各组件入口中。

公共库冻结 15 项 Public Shell API 及 12 个 `summary.env` 核心字段：`schema_version`、`component`、`run_id`、`status`、`started_at_utc`、`finished_at_utc`、`initiator_host`、`functional_check`、`recovery_check`、`failure_path_check`、`cleanup` 和 `exit_code`。状态只使用 `PASS`、`PARTIAL` 和 `FAIL`：授权型恢复未执行时不得提升为 `PASS`，必需断言、安全检查或 Cleanup 失败必须返回非零。Cleanup 在注册与执行阶段都检查当前 Owner，并要求目标包含 `m1_accept_<run-id>`、当前 run-id 且不属于禁止目标。实现禁止 `eval` 和任意 Command String，日志与证据必须对 Password、Secret、Token、Private Key、JDBC Password 和 Authorization 信息去敏。

本地 Git Bash syntax 与 Contract Test 只证明公共接口、失败退出和安全 Guard 的实现行为，不构成 MySQL、Hive、Kafka、Spark 或 DataX 的 VM Runtime Evidence。用户仍须在目标 VM 执行组件脚本并原样回传完整运行目录，由 M1 协调验收后才能改变组件证据状态。

### 理由

共享最小安全层可以让五个组件使用一致、可机器审查的 Evidence Layout 和状态语义，同时保持组件命令与恢复风险相互隔离。双重 Cleanup Guard、全新私有目录和统一去敏降低误删、证据覆盖和 Secret 泄漏风险；明确本地测试与 VM Runtime 的边界可防止证据等级被错误提升。

### 验证方法

公共库必须通过 Bash syntax、正常路径、强制失败、全部需初始化 Public API 的未初始化返回码、禁止越界写入、Secret 脱敏与非密码参数保持、错误 Owner 不注册、正确 Owner 注册并 Cleanup 成功等 Contract Test。`M1-CAS-07` 再执行跨组件静态 Contract Test；每个组件只有在目标 VM 保存完整 `summary.env`、步骤日志、固定功能结果、失败路径及适用的恢复与 Cleanup 证据后，才能单独评定运行状态。

### 影响与风险

`M1-CAS-02～06` 只能消费冻结 API，不得各自修改公共库。公共库缺陷会同时影响五个组件，因此任何接口、字段、状态或安全行为变化都必须先停止并行调用方、评估兼容性并重新运行公共及跨脚本 Contract Test。当前完成只提升共享库的本地实现证据，不改变五组件的 `candidate` 状态，也不解除 M2.5 或 Milestone 3 的直接门禁。

### 回滚方式

若冻结 Contract 被证明不可用，停止新的组件验收运行并保留已有 Evidence；经用户确认后新增替代决策，恢复到最后一个通过 Contract Test 的公共库版本，同步更新全部组件调用方和运行说明，再重新执行 M1-CAS-07 与受影响组件验收。不得通过复制五份安全逻辑、降低 Guard、删除失败证据或把 `PARTIAL` 改写为 `PASS` 规避回滚。

## DR-027：M1 组件验收降低证据门槛并按风险分级

- 状态：`accepted`
- 决策日期：2026-09-14
- 决策人：用户
- 影响范围：Milestone 1、M1-CAS-02～07、组件 Runtime 验收条件、Evidence Inbox 与 Trellis 收尾
- 替代决策：细化 `DR-026` 的能力优先原则；替代 `DR-025` 中将完整 Evidence Layout 作为组件状态提升必要条件的部分，不改变其接口、安全、去敏、Cleanup Guard 和失败语义

### 背景

M1-CAS-02 重新验收发现，现有流程把证明组件核心能力、支持故障诊断的增强证据和 Trellis 协作治理放在同一级 Acceptance Criteria 中。为补齐每条命令的独立输出、分目录附件、哈希和完整时间链而重复采集，已明显增加目标 VM 操作与协调审查时间，但对已由脚本控制流、关键结果和退出状态证明的能力只带来有限增益。

### 决策

M1 组件验收采用三级口径：

1. **Hard Gate**：必须证明后续阶段直接依赖的核心能力，以及可能造成数据破坏、Secret 泄漏或错误成功状态的安全行为。包括精确版本、启动或健康状态、必要的上下游连通、固定核心功能、失败非零或明确失败态、适用的恢复能力、破坏性操作显式授权、严格 Cleanup 边界和 Secret 去敏。
2. **Process Check**：Evidence Inbox 回传方式、Trellis 状态更新顺序和协调会话复核继续执行，但不再作为组件功能是否通过的独立阻断条件。发现流程缺口时补充记录，不推翻已经充分证明的核心能力。
3. **Optional Evidence**：每条命令单独文件、完整原始日志、分目录附件、逐文件哈希、Manifest 和完整时间链用于复现、审计与故障诊断；除非它们是判断某项 Hard Gate 的唯一可用依据，否则缺失时不单独阻断验收。

最小充分证据包为 `summary.env`、关键命令或断言的汇总输出、最终退出状态，以及可定位本次执行逻辑的 Git revision 或脚本 SHA-256。协调会话可以结合已经审查的脚本控制流判断证据：当脚本只有在必需断言全部成功后才能写入 `PASS`，对应脚本身份可核对且本次退出状态为 0 时，不要求每个内部断言再生成独立附件。涉及 restart、服务停止、数据删除或其他破坏性行为时，用户显式授权仍是 Hard Gate。

该口径适用于 M1-CAS-02：MySQL 版本、三节点连接与认证、ROW/FULL Binlog I/U/D、受控 restart 后健康与哨兵检查、严格临时 Database Cleanup 和失败退出属于 Hard Gate；独立 `recovery/` 目录、restart/health/sentinel 分文件、Evidence Inbox 原样回传以及 Trellis 状态提升顺序不再分别作为技术通过门槛。当前 M1-CAS-02 的脚本 Hash、`set -euo pipefail` 控制流、`summary.env` 中的 `recovery_check=PASS` 和最终 `exit_code=0` 可以共同构成恢复能力的充分证据。

### 理由

该分级将验收成本集中在会影响后续阶段、数据安全和结果真实性的风险上。对于当前个人学习与求职项目，核心能力可复现且关键失败不会被误报，比为所有内部步骤保存独立审计附件更有价值；保留增强证据为可选项，仍能在出现故障、状态矛盾或高风险变更时提高取证等级。

### 验证方法

协调验收逐项映射后续阶段依赖与 Hard Gate，核对最小证据包、脚本身份、关键结果和最终状态。只有在结果冲突、脚本身份不明、控制流不能保证失败传播、涉及未授权破坏性操作，或关键能力没有任何直接或间接输出时，才要求补充 targeted evidence。M1-CAS-02 按本口径可将核心功能与恢复结果评为通过；Trellis 状态和归档仍由协调会话单独更新。

### 影响与风险

该决策减少 M1 后续组件和收尾阶段的重复证据采集，但不降低 Secret、Cleanup、显式授权、失败传播和禁止破坏既有数据等安全要求。简化后的证据可能降低事后逐命令审计能力，因此遇到组件失败、版本漂移、脚本变更、状态矛盾或需要对外发布运行结论时，应按风险临时提升证据详细度。该决策不把 M1 临时兼容性链路扩大为 M2、M3 或 M9 的正式业务链路验收。

### 回滚方式

若精简证据导致核心能力无法复现、错误结果被接受或故障无法定位，保留已有证据和失败记录，由新的连续决策恢复受影响组件的详细证据要求，并只对相关风险路径补采；不得无差别要求所有组件重跑，也不得删除基于本决策形成的历史验收记录。

## DR-031：离线 Pilot 收口与 V2 按层规模化开发路线

- 状态：`accepted`
- 决策日期：2026-09-27
- 决策人：用户
- 影响范围：Milestone 2～6、正式源库、Mock 数据生成、MySQL 初始化、ODS/DWD/DIM 实施方式、验收 Gate、Pilot 历史资产

### 背景

100 单 `hist-v1-001` 已在限定环境完成 MySQL `biz_order` → DataX → HDFS/Hive ODS → Spark SQL on YARN → Hive DWD，并形成 ODS/DWD 100↔100、88 分区、69 `PAID`、31 `CANCELED`、8,372,600 payable cents、0 mismatch 的验收结果。该 Pilot 已证明 DataX MySQL Reader/HDFS Writer、ORC + Snappy、Hive 外表与分区、Stage → Validate → Publish、Spark SQL ODS→DWD、历史批量处理、失败保护，以及两条 Flink 长任务与 Spark 离线任务并发的可行性。

继续按 `order → order_item → payment → refund` 逐表完成 ODS/DWD 小样本闭环，会重复验证已经证明的通用能力，并使正式 21 表数据源、跨表关系和分层模型长期停留在 Pilot 边界。用户因此确认离线开发从小样本 Pilot 切换到 V2 Source Data Build 与按层批量实施。

### 决策

1. `hist-v1-001`、100 单生成器、已验证的 `ods_order` / `dwd_order` 及相关脚本统一作为 `PILOT / ACCEPTANCE / HISTORY` 保留。它们的历史证据继续有效，但不再作为正式 V2 数据开发入口。
2. 正式源库统一为 MySQL `ecommerce_oltp`。`ecommerce_oltp_m2_acceptance` 保留为 Pilot、CDC、R1/R2/M3 历史验收环境，不删除，也不作为正式离线开发源。
3. 正式数仓沿用 `ecommerce_ods`、`ecommerce_dwd`、`ecommerce_dim`、`ecommerce_dws`、`ecommerce_ads`，不新增 `_v2` database。V2 正式装载前必须通过单独批准、可验证、可回滚的初始化方案隔离或重置现有 Pilot 数据，不允许混用。
4. V2 数据生成固定为 Python Generator → CSV → MySQL `LOAD DATA`。Generator 只负责业务关系、状态流转、时间分布、主外键、金额平衡、优惠分摊、支付重试、退款、身份关系和边界场景；数据库装载由 `LOAD DATA` 负责。旧 100 单 Generator、Python 逐条 INSERT 和 `generate_and_insert.py` 不作为 V2 正式路径。
5. 正式源模型继续采用 `DR-028` 的 7 个业务域、21 张 `biz_*` 业务表。生成器统一覆盖一期 21 表，不再为每张表单独补小样本。
6. 工程实施从逐表纵向 Pilot 改为按层批量推进：21 表 Source → Source Gate → 批量 ODS → ODS Gate → DWD/DIM → Model Gate → DWS → ADS → Doris → 最终整链路验收。
7. ODS 收敛为“一套代码 + 多表配置”：通用 DataX Job Generator、Stage Runner、Spark Validation 和 Publish；每表配置 source table、target table、columns、primary key、partition rule、extract rule 和 quality rule。
8. DWD/DIM 的业务转换 SQL 按表维护；Spark 提交、日志、锁、失败保护、参数解析和 precheck 使用通用执行框架。
9. 不再执行 `ods_order_item_create.sql` 的 Pilot 路线。该文件保持 F2 `CONFIRMED_CREATED / NOT EXECUTED`，不提升为 VERIFIED，也不自动成为 V2 正式 ODS 设计。
10. 不取消测试。验收收敛为 Source Gate、ODS Gate、Model Gate 和最终整链路验收，减少重复逐表端到端步骤，同时保留失败非零、结果守恒和跨表一致性要求。

### 验证方法

1. Source Contract：核对 `ecommerce_oltp` 正式 21 表 DDL，并冻结每表数据量、时间范围、状态分布、跨表比例、CSV 字段、依赖和生成顺序。
2. Source Gate：在固定 Generator 版本、seed 和显式时间范围下生成全部 CSV，经 `LOAD DATA` 装载后核对 21 表行数、业务键、主外键、金额平衡、状态关系与预期失败场景。
3. ODS Gate：核对全部一期源表与 ODS 的行数、主键唯一性、关键字段、分区及核心跨表关系；发布失败必须返回非零且不得覆盖已验证分区。
4. Model Gate：核对订单↔明细、订单↔支付、订单↔退款、商品关系、金额守恒和进入范围的核心指标。
5. 最终验收：DWS、ADS、Doris 完成后执行逐层对账、首次运行、重跑、回补、重复输入和失败阻断验证。
6. 当前只完成方向冻结；具体规模、时间范围、比例、DDL 核对、Generator、CSV、`LOAD DATA`、各 Gate 和数据库重置均须以未来文件与 Runtime 证据验收。

### 影响与风险

该决策停止继续扩展 Pilot，能够把工程投入集中到正式 21 表数据和跨表业务闭环，并让 ODS 通用框架成为主要复用点。风险是一次性批量范围扩大后，源 Contract、生成顺序、资源容量、MySQL 装载、ODS 配置或跨表质量问题可能集中暴露，因此必须先冻结规模与分布，再进入实现，不能以“大规模”名义虚构数据量或跳过 Gate。

当前 `ecommerce_oltp` 的 21 表 DDL 尚待核对；V2 规模、时间范围、状态分布和跨表比例仍为 `DECISION_REQUIRED`。现有 `ecommerce_ods` / `ecommerce_dwd` Pilot 数据的精确重置对象、备份、回滚和验收方式也需单独确认，本决策不授权立即执行数据库清理。`BI / Agent` 是否进入当前 V2 交付仍与 `DR-029` 的后续规划边界存在待确认项，不阻塞 Source Data Build，但不得据此开始实现。

### 回滚方式

若 V2 Source Contract 或批量路径在当前资源下不可实施，保留本决策、全部 Pilot 验收资产、失败证据和已生成的只读数据，由新的连续决策调整规模、分批策略或 Gate，不删除 `ecommerce_oltp_m2_acceptance`，不把 Pilot 数据混入正式 V2 数据，也不静默恢复逐表 Pilot 作为正式主线。数据库初始化或重置只有在备份/隔离、精确目标、验证与回滚方案单独批准后执行。

- 关联决策：延续 `DR-028` 的 21 表业务基线、`DR-029` 的 Java DataStream Jar + YARN Application Mode 和 `DR-031` 的 Shared V2 Source Data Build；替代 `R4 Payment DWD` 作为当前下一步，但不撤销 R1～R3 的历史 Runtime 事实

### 背景

实时 R1～R3 已在 `ecommerce_oltp_m2_acceptance` → `ods_cdc_m2_clean_v1` → Order / OrderItem DWD → Doris 的限定范围证明 21 表 Snapshot、Binlog 增量、Checkpoint 恢复和正常顺序 Upsert。继续按 Payment、Refund、Coupon 逐表复制完整验收，会维持离线与实时两套业务源，并形成大量长期 YARN Application；Pilot 的 `all-to-zero` 与单一 `kafka_offset` Sequence 也不能直接扩展到正式多分区 V2。

### 决策

1. R1～R3 统一定位为 `PILOT / ACCEPTANCE / HISTORY`。`OrderDwdJob`、`OrderItemDwdJob` 不删除，作为 `VERIFIED PROTOTYPE / FRAMEWORK REFERENCE` 保留；`R4 Payment DWD` 暂停。

3. 历史初始化采用 Python Generator → 21 CSV → `LOAD DATA`；实时增量由独立 Incremental Business Generator 通过 MySQL Transaction 产生 Binlog，禁止直接写 Kafka。
4. 正式 CDC 初始化顺序为 Source Gate → 停止源写入 → Flink CDC Initial Snapshot → Kafka Snapshot Gate → 冻结 Snapshot 基线 → 启动 Incremental Business Generator → 持续增量。
5. 正式 CDC 覆盖一期 21 表。`ods_cdc_m2_clean_v1` 与旧污染 Topic 不复用；先做 Topic Inventory，再冻结 Formal Topic Namespace。
6. `all-to-zero` 只保留为 Pilot 策略。正式 Key/Partition 保证 Same Business Key → Same Partition → Ordered Events；具体 Partition 数待数据规模冻结。
7. `kafka_offset` Sequence 只保留为单 Partition Pilot 策略。正式 `event_version` 须结合 CDC source metadata、Binlog/transaction metadata、source timestamp、partition+offset 或业务更新时间另行冻结。
8. Flink 工程按业务域组织 Domain Applications；Kafka Source、CDC Parser、Router、Metadata、Checkpoint、Error Handling、Doris Sink、YARN 提交、日志和恢复框架通用化，业务 Transform 分业务维护。不再一张表一个长期 Application。
9. V2 实时验收收敛为 CDC Gate、Realtime Model Gate、Recovery Gate、实时指标验收与 Offline ↔ Realtime Reconciliation，不逐表重复完整 Initial + Incremental + Recovery 大验收。
10. Pilot Checkpoint Root 不用于 V2。正式 CDC、DWD/DIM、DWS/ADS 分别使用隔离的 Checkpoint Root。
11. 正式 V2 启动前，Doris Pilot 数据必须按另行批准、可验证、可回滚的方案清除或隔离；继续使用正式 database 命名，不创建 `ecommerce_serving_v2`。本决策不授权立即执行数据库清理。

### 理由

统一业务源、模型和指标合同可以避免离线与实时长期使用不同数据基线和口径。Domain Application 与通用运行框架减少长期 YARN Application 数量和重复工程，同时保留业务转换逻辑的可读性。集中 Gate 保留必要的完整性、恢复和对账验证，又避免把已由 Pilot 证明的通用能力逐表重复执行。

### 验证方法

1. Shared Source Gate：固定 Generator 版本、seed 和显式时间范围，核对 21 CSV 与 `ecommerce_oltp` 的行数、主外键、金额、状态、时间和跨表关系。
2. CDC Gate：核对 21 表 Snapshot 行数、主键、`source.db/table`、CDC op、Key/Partition、`event_version`，并验证代表性 INSERT/UPDATE/关键 DELETE。
3. Realtime Model Gate：核对 Order↔OrderItem、Order↔Payment、Order↔Refund、Coupon、Product、Identity 的状态、金额、Upsert 和重复通知语义。
4. Incremental Simulation：增量生成器经 MySQL Transaction 产生支付失败→成功、取消、退款、券、身份和商品变化，不直接写 Kafka。
5. Recovery Gate：集中验证 JobManager/TaskManager Failure、Checkpoint Restore、Kafka Resume、Doris 无重复与无数据丢失。
6. 指标验收：同一截止时间下执行 Offline ↔ Realtime Reconciliation，并在确认的延迟范围内解释差异。
7. 当前只完成方向冻结；以上内容只有在文件、命令、运行环境和结果对账齐全后才能标记 `VERIFIED`。

### 影响与风险

## DR-034：V2 正式数据规模、21 表候选 Contract 与本地生成基线

- 状态：`accepted`
- 决策日期：2026-10-12
- 决策人：用户
- 影响范围：Milestone 2～3、21 表 MySQL 源模型、Business / Behavior Generator、CSV Contract、`LOAD DATA`、Source Gate、性能实验
- 关联决策：延续 `DR-028` 的 21 表业务模型、`DR-031` 的 Python → CSV → `LOAD DATA` 路线和 `DR-032` 的离实时统一 Source Gate；更新 `DR-033` 中“尚无 21 表候选 DDL”的时点事实

### 背景

用户确认新 Generator 不建设独立 Smoke 数据规模档位：正式数据规模承担业务与指标验收，性能实验规模在正式规模通过后单独执行。目标 MySQL 只读检查显示，正式库 `ecommerce_oltp` 仅有 3 张技术测试表，没有 21 张 `biz_*`；历史验收库有同名 21 表和 Pilot 数据，可作为字段参考但不能直接代表正式库。

历史验收结构与当前业务、指标和物理模型主体一致，但 CSV Contract 缺少 4 个审计字段，订单和优惠券之间的双向外键会形成循环装载依赖。旧候选稿的约 12,000 条商品变更事件也与“4,000 SKU 中约 25% 变化、每 SKU 1～3 个版本”不相容。

### 决策

1. 数据规模只保留两档：正式数据规模为 90 天、100,000 笔订单、约 285,000 条订单明细、约百万级 OLTP 记录和 3,000,000～5,000,000 条行为事件；性能实验规模为约 900,000 笔订单和 9,000,000 条行为事件。仓库中的 `smoke.json` 仅作快速单元测试 Fixture。
2. 新增 `mysql/ddl/001_ecommerce_oltp.sql` 作为 21 表候选 DDL。Business CSV Contract 补充 `biz_order_item.updated_at`、`biz_payment_attempt.created_at`、`biz_refund_request.created_at`、`biz_refund_transaction.created_at`；MySQL 生成列不进入 CSV。
3. 订单和优惠券采用单向物理 FK：保留 `biz_order.coupon_id → biz_coupon.coupon_id`；`biz_coupon.locked_order_id`、`used_order_id` 只建索引，反向关系由 Generator 与 Source Gate 校验，避免循环 FK 阻碍 21 CSV 装载。
4. `biz_product_change_event` 正式目标调整为约 2,000 行，保持约 25% SKU 变化、每个变化 SKU 1～3 个版本的业务分布。
5. 修复订单注册、支付、优惠券、退款、购物车和行为采集的跨表身份/状态时间问题；固定参数下必须满足相同输出、`event_time ≤ ingest_time ≤ history_end`、订单不早于用户注册、券不晚于锁定发放且券用户与订单用户一致。
6. 本地正式规模生成通过只提升 Generator 在记录参数下的证据状态，不提升候选 DDL、MySQL 装载、Source Gate、CDC 或 ODS 状态。Behavior 在正式交付前必须读取 Business 实体快照/Manifest，不得只根据相同数量重新构造实体空间；该门禁后由 `DR-035` 闭合。
7. 本决策不授权数据库 DDL/DML、`LOAD DATA`、正式库清理或 Pilot 数据迁移；这些操作继续要求单独批准。

### 理由

单一正式规模可以直接验证业务规则和指标可计算性，避免维护没有交付价值的第三档数据。单向 FK 保留订单用券的核心数据库约束，同时消除批量装载循环；反向状态仍通过集中 Source Gate 验证。约 2,000 条商品变更事件能够与 SKU 变化比例和版本数同时成立。先在本地完成确定性正式规模生成，可以在数据库变更前暴露时间、身份和规模问题，但不能替代数据库约束和跨表 SQL 验收。

### 验证方法

1. 静态比较候选 DDL 与 `TABLE_COLUMNS`：21 表集合一致、可写字段差异为 0；生成列仅保留在 DDL。
2. 检查 DDL 不含 `DROP`、`TRUNCATE`、`DELETE`、`INSERT` 或 `IF NOT EXISTS`，不存在向后 FK 依赖和优惠券反向循环 FK。
3. Business Targeted Unit Test 验证确定性、金额守恒、支付时序、订单注册、优惠券用户/事件时序和历史窗口；Behavior Targeted Unit Test 验证确定性、事件类型及 `event_time ≤ ingest_time ≤ history_end`。
4. 2026-10-12 本地正式规模实测：Business 生成 21 张 CSV、100,000 笔订单、285,000 条订单明细、合计 1,329,480 行、147,089,462 bytes，90 天时间越界为 0，耗时 65.743 秒。
5. 同日本地 Behavior 正式下限实测：3,000,000 条事件、925,398,094 bytes，五类事件均有数据，耗时 422.308 秒。
6. 后续 Runtime 验收必须在单独授权后部署候选 DDL、执行版本化 `LOAD DATA`，并以 Source Gate 核对行数、PK/FK、状态、金额、时间、优惠券反向关系、失败非零和幂等重跑。

### 影响与风险

候选 DDL、CSV 字段和正式规模已经形成可执行基线，Generator 的已知身份与时间错误已修复。本地生成耗时受当前 Windows 环境、Python 版本和磁盘影响，不能作为服务器导入吞吐或性能实验结论。DR-034 形成时 Behavior 尚未复用 Business Entity Manifest，该项后由 `DR-035` 闭合；数据库 CHECK/FK、优惠券最低消费、完整状态分布、跨表比例、`LOAD DATA` 幂等和 Source Gate 仍未验证。性能实验规模仍为 `DESIGNED / not_run`。

### 回滚方式

若候选 DDL 在隔离部署或 Source Gate 中失败，保留本决策、本地生成结果和失败证据，回滚本次候选 DDL、CSV Contract 与 Generator 修改，不修改或删除历史 acceptance 环境。若单向 FK 无法满足业务一致性，通过新的连续决策调整 Source Gate 或关系设计，不静默恢复循环 FK。任何已授权的数据库实验必须使用独立目标、明确备份/回滚和可验证 Cleanup；不得覆盖现有正式库或混入 Pilot 数据。

## DR-035：Business Entity Manifest 与 Behavior 实体绑定 Contract

- 状态：`accepted`
- 决策日期：2026-10-12
- 决策人：用户
- 影响范围：Milestone 2、Business / Behavior Generator、身份映射、Session、历史 Behavior、Continuous Behavior
- 关联决策：落实 `DR-034` 中 Behavior 必须复用 Business 实体空间的门禁；保持 `DR-031`、`DR-032` 的 Source Gate 和数据库授权边界不变

### 背景

此前 Business 与 Behavior 只共享配置中的实体数量。即使双方都生成相同范围的整数 ID，也不能证明用户、访客、身份版本、SKU 和有效时间来自同一数据集；Behavior 还可能在身份映射生效前填入 `user_id`。直接把身份映射记录中的登录 `session_id` 用于全部后续行为，又会把跨 90 天事件错误合并为单一 Session。

### 决策

1. Business Generator 每次输出 `entity_manifest.json`，当前 `entity_manifest_version=1`。Manifest 记录数据版本、Generator 版本、Seed、时区、历史范围，以及用户注册时间、访客首次出现时间、身份映射有效区间和 SKU 实体关系。
2. `dataset_manifest.json` 记录 Entity Manifest 的文件名、版本和 SHA-256，使 Behavior 结果能够绑定到精确的 Business 实体快照。
3. Behavior Bootstrap 与 Continuous CLI 都必须显式传入 `--entity-manifest`。缺失文件、未知版本、时区/历史范围不匹配、实体数量不匹配、重复 ID、未知引用或倒置的身份有效区间必须 fail-fast。
4. Behavior 的 `user_id`、`visitor_id`、`sku_id` 和 `identity_version` 只从 Manifest 读取；配置中的 `entity_counts` 仅作契约核对，不再用于重新构造 ID。
5. 同一运行批次内按访客对事件时间排序；连续 30 分钟无活动才开启新 Session。`event_id` 使用数据版本、Seed 和运行时间范围派生的命名空间，避免不同范围批次仅按行号生成重复 ID。
6. 当前正式规模证据覆盖 Bootstrap Historical Behavior。Continuous 跨批次 Session 延续仍需在正式 Kafka/Checkpoint Contract 中设计和验证，不由本决策提升为 `verified`。
7. 本决策不授权数据库 DDL/DML、`LOAD DATA`、Source Gate、Kafka 写入或目标 ECS 变更。

### 理由

显式 Entity Manifest 将“数量相同”提升为可验证的同一实体快照，并保留身份映射的有效时间。SHA-256 让 Behavior Manifest 能定位精确输入。按访客小批排序可实现 30 分钟 Session 规则，同时避免把 300 万事件整体载入内存；把数据库装载留在独立门禁可保持当前改动可逆。

### 验证方法

1. Business Targeted Test 验证 Entity Manifest 确定性、实体数量和 Dataset Manifest SHA-256；Behavior Targeted Test 验证未知版本 fail-fast、确定性、实体引用和 30 分钟 Session 边界。

## DR-036：V2 版本化 LOAD DATA 与 Shared Source Gate Contract

- 状态：`accepted`
- 决策日期：2026-10-12
- 决策人：用户
- 影响范围：Milestone 2～3、Business Generator、21 表 CSV/Dataset/Entity Manifest、MySQL Source Load、Shared Source Gate、离线 ODS 与 Formal CDC 进入门禁

## DR-037：60 天历史初始化、30 天双链路回放与拉链维度

- 状态：`accepted`
- 决策日期：2026-10-13
- 决策人：用户
- 影响范围：Milestone 2～6、8～9、Business / Behavior Generator、DataX/Hive ODS、DIM/DWD、Formal CDC、Kafka/Flink、Doris、重跑与离实时对账
- 关联决策：细化 `DR-034` 的 90 天正式数据规模、`DR-036` 的 Shared Source Gate 之后接续、`DR-031` 的批量 ODS 路线与 `DR-032` 的 Formal CDC 路线；不替代既有 Source Gate 或 Pilot Runtime 证据

### 背景

现有正式 bundle 一次性生成并装载了 90 天结束时的 21 表最终状态，能够证明规模、Schema、引用、状态、金额和 Source Gate，但不能证明历史初始化与后续增量之间不存在遗漏、重复或未来状态泄漏，也不能验证 DataX 水位、历史分区重算、CDC Snapshot/Binlog 接续、离实时逐日接管和 SCD2 维护。

需要把同一套 90 天确定性业务过程转换为可按时间推进的验收输入，在保留既有正式源证据的同时，为批量 ODS、Formal CDC、DIM 拉链和离实时对账提供统一切换点。

### 决策

1. 正式观察窗口仍为连续 90 个业务日；前 60 天定义为历史初始化窗口，`cutover_time` 固定在第 61 个业务日零点，后 30 天定义为逐日双链路回放窗口。所有任务显式接收时间范围，窗口采用左闭右开语义，不使用执行机器当前日期。
2. Generator 后续应输出截至切换点的 `bootstrap` 以及 `day_61`～`day_90` 每日操作包。每日包同时表达新增、更新、失效/删除、状态事件、维度变化和预期对账；交易增量必须通过 MySQL Transaction 形成 Binlog，不得直接写 Kafka 伪造 CDC。
3. 初始化源状态必须是 `cutover_time` 时点的正确状态，不得包含后 30 天才发生的最终变化。现有 90 天最终 bundle 与 1,328,502 行 Source Gate 证据继续有效，但不作为 60/30 时间推进式回放已经实现或验证的证据。
4. 离线初始化完整抽取切换点前的历史。事实和事件按各自业务发生日期发布到 Hive ODS `dt`；维度全量快照按快照日期保存。后 30 天可变表按可靠的源更新时间水位抽取，Append-only 事件按记录水位抽取，再依据业务时间重建受影响的历史业务分区。
5. Formal CDC 在暂停源写入后，以与离线初始化一致的源端切换点执行 Initial Snapshot 并记录 Binlog Offset。Snapshot 只初始化源状态，不能作为第 61 天新增交易重复累计；后 30 天操作包逐日写入 MySQL，CDC/Flink 负责低延迟结果。
6. 链路统一区分业务发生/生效时间、源更新时间、抽取时间、装载时间、业务日期、批次和 CDC Offset。业务时间决定事实/事件分区或维度版本，源更新时间决定增量范围，抽取/装载时间只用于审计。
7. 切换点前历史结果由离线链路建立基线；切换点后实时链路负责尚未离线结算的开放业务日。每日离线 Gate 通过后，离线结果逐日接管已结算日期；服务层必须通过结算边界或版本选择避免离线和实时结果重复相加。
8. SCD2 只用于需要按历史属性还原事实的维度。前 60 天必须由带 `effective_at` 的变更事件、可靠增量历史或每日快照差异构建完整版本；只有第 60 天快照时，拉链只能从切换点开始。后 30 天按业务生效时间关闭旧版本、插入新版本；迟到变化重新生成受影响业务键的完整时间线。稳定且只关心当前值的维度使用 Type 1。
9. ODS、DIM/DWD 和运行审计必须可追溯 `business_time`/`effective_at`、`source_updated_at`、`extract_time`、`load_time`、`business_date`/`dt`、`batch_id`、来源、操作类型和 CDC Offset；具体字段映射按源表能力实现，不得用数仓 `load_time` 冒充源端水位。
10. 详细 Contract、数据流、SCD2 算法、质量规则和证据边界以 `docs/design/historical-incremental-replay-design.md` 为准。本决策不授权重置现有 MySQL、重新装载数据、创建 Topic、启动 Formal CDC、清理 Doris 或执行正式回放。

### 理由

60 天历史窗口足以验证跨日订单、支付、退款、身份和商品历史，后 30 个日批又能覆盖连续水位、重跑、回补、迟到和故障恢复，而不需要为每一天维护独立最终数据集。统一切换点使 DataX 与 CDC 能在同一业务状态上接续；把业务时间、源更新时间和装载时间分开，可以同时保证业务归属、增量捕获和运行审计。对小规模维度采用受影响键重建或整表原子覆盖，比为个人项目引入额外事务表格式更容易验证和维护。

### 验证方法

1. 固定 Seed 重复生成 `bootstrap`、30 个 daily package、Manifest 与预期结果，逐文件 SHA-256 一致。
2. 在隔离源库只装载前 60 天，核对截至切换点的当前状态和历史事件，并证明不存在切换点后的字段值或事件。
3. 记录同一切换点的源表基线、DataX 水位和 Binlog Offset；验证 DataX 历史初始化、CDC Initial Snapshot 与第一个增量窗口之间无重复、无缺失。
4. 验证前 60 天事实按业务日期分区，30 个日批水位连续；历史记录后续变化能够重建原业务日期分区，同窗口重跑结果确定。
5. 验证每日 MySQL 操作产生预期 CDC `INSERT/UPDATE/DELETE`，Flink 中断恢复后可从已确认位置接续，Snapshot 记录不被重复统计为新交易。
6. 对 SCD2 检查当前版本唯一、有效区间合法且不重叠、相同属性不重复开版、历史事实只命中一个版本、迟到变化重算与重跑幂等。
7. 每日执行源端、ODS、DIM/DWD、实时 Doris 与离线结果的主键、行数、状态和金额对账；失败必须返回非零并阻断接管。

### 影响与风险

Generator 需要从“最终 90 天快照 bundle”扩展为“切换点状态 + 每日业务操作”，DataX 需要区分抽取水位和业务分区，DIM 需要增加历史版本构建，Formal CDC 需要一致切换点与 Snapshot/增量边界。当前 21 表是否为所有候选 SCD2 属性保留了完整前 60 天变化仍需实施核对；缺少历史时只能从切换点开始，不能补造版本。历史 Behavior 的批量装载入口、正式 Topic/Partition/Schema、Flink Watermark/迟到/状态 TTL、Doris 接管模型和离实时阈值仍受后续门禁约束。

当前正式 MySQL 已包含完整 90 天最终状态，不能直接作为新的切换点源库使用。任何隔离库构建、正式库重置、Topic 或 Doris 处理都是独立外部操作，必须获得对应授权并保留回滚证据。

### 回滚方式

若 60/30 生成或链路验收失败，保留 `DR-037`、失败 Manifest、日志和对账结果，停止后续 Gate；删除或隔离操作只针对经授权创建且有明确运行编号的 replay 资源。现有 90 天正式 bundle、正式 MySQL、Source Gate、Pilot ODS/CDC 历史证据保持不变。通过新的连续决策调整切换比例、输入 Contract 或历史策略，不改写本决策，不复用 Pilot Offset/Checkpoint，也不降低质量规则绕过失败。

## DR-038：DataX 字段权威与批次隔离发布 Contract

- 状态：`accepted`
- 决策日期：2026-10-13
- 决策人：用户
- 影响范围：Milestone 3、DataX 多表配置与 Job Generator、HDFS staging、Hive ODS 分区、字段 Contract、审计、重跑和 ODS Gate
- 关联决策：细化 `DR-001` 的“直写 ODS”物理边界、更新 `DR-031` 的逐表 columns 描述，并落实 `DR-037` 的抽取水位与业务分区分离原则；不改变 Source Gate、正式 CDC 或数据库授权边界

### 背景

当前 21 表 DataX Job Generator 已使用统一配置描述抽取策略、主键、分区和质量规则。若每表重复维护 columns，会与 Business Generator 的 CSV 字段顺序及正式 MySQL DDL 形成多套权威来源；若 DataX 直接写最终 `dt`，一次抽取包含多个业务日期或发布中途失败时，难以在校验前保证最终分区原子性。

### 决策

1. DataX 字段顺序唯一引用 Business Generator 的 `TABLE_COLUMNS`；字段类型以正式 MySQL DDL 为权威。`ods_tables.json` 不重复维护逐表 columns 清单，但必须逐表声明 source/target、primary key、partition、extract 和 quality rules。字段 Contract 变化必须同步 Generator、DDL 映射和测试。
2. DataX HDFS Writer 将 ORC + Snappy 写入 `<ODS_STAGE_ROOT>/<target_table>/batch_id=<batch_id>` 批次隔离路径。该路径属于 ODS 发布过程的临时工作区，不是独立持久化数据层。
3. Spark Validation / Publish 在文件、Schema、主键、行数和业务质量检查通过后，根据每行 `business_date` 或显式快照日发布并注册最终 Hive `dt` 分区。失败批次不得暴露为已发布分区；重跑必须保持批次隔离和明确覆盖边界。
4. 当前抽取策略分为 `mutable_incremental`、`append_only` 和 `full_snapshot`。可变表使用可靠 `updated_at` 半开窗口，Append-only 表使用 `recorded_at` 或 `merged_at` 半开窗口；`biz_identity_mapping` 因 `recorded_at` 无法捕获后续撤销和 `effective_to` 补写而使用每日全量快照。
5. 抽取水位只决定本批读取范围，不决定最终业务分区。事实和事件按行业务时间生成 `business_date`，全量快照按显式快照日分区；`extract_time`、`load_time` 和 `batch_id` 只作运行审计。
6. 生成的 DataX Job 只能写入项目 Runtime 目录及 ODS staging 根路径，文件权限保持私有；数据库密码只从环境变量读取，不进入参数、日志、Manifest 或版本库。

### 理由

字段顺序和类型各保留一个权威来源，可以避免 21 份重复列表随 Schema 演进产生漂移。批次隔离后再校验和发布，能够处理一个抽取窗口覆盖多个业务日期、迟到变化重建历史分区以及失败重跑，同时保持“不建设持久化中间层”的架构边界。三类抽取策略显式表达源表是否可变以及水位可靠性，比对所有表套用 `updated_at` 更可验证。

### 验证方法

1. 解析 `datax/config/ods_tables.json`，确认覆盖 21 表：14 张 `mutable_incremental`、6 张 `append_only`、1 张 `full_snapshot`，且所有表的分区来源均为 `business_date`。
2. 执行 `tests/datax/test_generate_job.py`，验证 bootstrap 多业务日期分布、半开水位、身份映射快照、缺失/反向时间窗口、未知配置键、目录穿越、符号链接逃逸、私有文件和环境变量失败路径。
3. 执行仓库 `tests/run_unit.sh`，确认 Business、Behavior、DataX 和 MySQL 静态测试全部通过；执行 `git diff --check` 和 Markdown 本地链接检查。

### 影响与风险

## DR-043：Replay Batch Ledger 与批量范围验收

- 状态：`accepted`
- 决策日期：2026-10-16
- 决策人：用户
- 影响范围：Milestone 2～3、MySQL Daily Replay、批量回放、幂等重跑、断点恢复与验收方式
- 关联决策：落实 `DR-037`、`DR-040` 的 Day 61～90 时间推进式回放，不改变 Dataset、业务语义或 Shared Source Gate

### 背景

逐日人工启动和验收使 Day 61～90 被拆成 30 个重复 Gate，进程中断后又容易从固定首日重新尝试。仅依赖本地结果文件无法证明目标数据库是否已提交，也不足以安全区分“已提交但结果文件未写完”和“数据库未提交”。

### 决策

1. 采用数据库 `replay_batch_ledger` 记录已提交批次，以 `batch_id` 和 `day_number` 唯一约束绑定 Business Hash、Package Manifest Hash 与操作数。
2. Daily 业务操作、Ledger 写入和 45-rule Source Gate 必须位于同一事务；Gate 失败时全部回滚。
3. 同一 Day、相同 Hash 与操作数的重跑返回 `already_applied`，不重复执行业务 SQL；同 Day 输入冲突必须 fail-fast。
4. Day 61～90 使用 Range Executor 一次推进。运行前完成完整范围 Preflight，运行中按日保存 Checkpoint/Acceptance；中断后通过 `--resume` 核对本地证据、数据库 Ledger 和实时 Gate，从一致位置继续。
5. 每日只作为自动 Checkpoint 和失败定位点，不作为用户逐日验收 Gate；完整范围结束后统一执行 Ledger、Expected Result、Source Gate、权限和证据完整性验收。
6. 该模式后续可用于 DataX/ODS 等批量阶段的工作流设计，但不直接复用 MySQL Ledger 表；各阶段使用自身适用的批次状态、幂等发布和质量规则。

### 理由

数据库 Ledger 能把提交事实与业务写入绑定，Range Executor 能减少人工轮询和重复验收，同时保留逐日定位与安全恢复能力。相比继续逐日人工推进，新增代码和表结构成本较小，能够直接降低误重放、状态漂移和长任务中断后的恢复风险。

### 验证方法

1. Unit Test 覆盖 Ledger 校验、相同输入幂等、冲突拒绝、完整范围 Preflight、Checkpoint 与 Resume 状态核对。
2. 隔离 MySQL Integration Test 证明 Day 72 首次提交、同日重跑不重复写入，以及 Day 73 Gate 失败时 Ledger 与业务数据共同回滚。
3. 正式范围完成后核对 30 个 Ledger Day、30 份 Acceptance、Day 90 Expected Result、独立 45-rule Source Gate、`local_infile=OFF` 和最小权限回收。

### 影响与风险

### 回滚方式

在未执行新批次时可停止使用 Range Executor，但已经写入的 Ledger 是已提交业务批次的审计事实，不得单独删除。若实现存在缺陷，应保留数据库、Ledger、Checkpoint 和日志，修正 Executor 后从一致状态 `--resume`；数据库重置、数据删除或 Ledger 清理仍需新的破坏性 Database Operation 授权。

## DR-044：采用 r6 作为正式 Business Replay Baseline

- 状态：`accepted`
- 决策日期：2026-10-17
- 决策人：用户
- 影响范围：Milestone 2～3、8～9、Business Replay 固定输入、ODS/CDC 输入绑定、验收证据与状态文档
- 关联决策：替代 `DR-040` 中 `c690b325...` 的当前 Baseline 地位；保留 `DR-040`、r3 `4abcd890...` 及其历史证据，不重写历史运行事实

### 决策

1. 当前正式 Business Replay Baseline 使用 Dataset Version `v2.3-replay-formal-20260105-r2`，并以 Business Hash `ecea32d620bfbf44671ff2c1e1ff765fe4638f330f621229b9dd8f543578deb5` 与 Replay Manifest SHA-256 `5e09633896125c487a9a2d55632507621eb058679f4e30bc83c313c42e46533c` 精确标识。

5. 本决策只确认 Business Replay 输入及其 MySQL Runtime，不提升 Behavior、ODS、Kafka、CDC、Flink、Doris 或下游模型状态。

### 验证方法

## DR-045：正式 ODS 使用独立显式根路径并保留 Pilot History

- 状态：`accepted`
- 决策日期：2026-10-17
- 决策人：用户
- 影响范围：Milestone 3、Hive ODS Schema、HDFS 路径、Pilot 历史资产、DataX Job 导出与回滚边界
- 替代决策：无

### 背景

正式 `ecommerce_ods` 仍存在三张 2026-09-21 Pilot 表，其中旧 `ods_order` 使用 Hive 默认 warehouse 路径并注册 88 个历史分区。直接用新 21 表 DDL 覆盖会造成同名表和物理路径冲突；继续只在隔离库运行则不能形成正式 Source → ODS 证据。仓库此前也只有 Runtime job，没有可见的无 Secret DataX job 导出。

### 决策

1. 将三张旧 Pilot 表重命名为 `pilot_20260921_*` HISTORY 名称，保留其 EXTERNAL HDFS 数据、分区和原 LOCATION，不删除、不覆盖。
2. 正式 21 张 ODS 表固定为 EXTERNAL、ORC + Snappy、按 `dt` 分区，显式路径为 `/warehouse/ecommerce/ods/<target_table>`。
3. Seed `20260928` 的终态正式 Source 使用 Snapshot Contract 执行一次正式 Bootstrap；Seed `20260105` Replay 继续承担时间推进式增量、恢复和回补验收，两者证据不得混用。
4. `datax/jobs/` 保存仅含占位符的可审计 job 与 SHA-256 Manifest；Secret 仅在私有 Runtime 临时注入并在运行后删除。

### 理由

显式新根路径把正式 21 表与 Pilot warehouse 路径物理隔离；元数据 rename 保留历史数据且具备清晰回滚映射。正式 Snapshot Bootstrap 直接证明现有 `ecommerce_oltp` 到正式 ODS 的完整规模链路，同时不替代 Replay 的时间推进式 Acceptance。

### 验证方法

1. Hive 盘点确认三张 Pilot 表重命名后仍为 EXTERNAL，旧 `ods_order` 原 LOCATION、88 分区和 194,126 bytes 保持。
2. 正式 Batch `formal-bootstrap-20260228-r1` 状态为 `planned → staged → validated → published`。
3. 正式 Source 21 表逐表行数与 Dataset Manifest 一致，合计 1,328,502；独立 ODS Gate 为 1,476/1,476、0 失败。
4. `SHOW GRANTS` 与文件检查证明临时正式源 `SELECT` 已回收，hadoop202 `datax.env` 和临时 Secret job 已删除。

### 影响与风险

任何依赖旧表名 `ecommerce_ods.ods_order` 作为 Pilot 的脚本必须改用 HISTORY 名称；正式 `ods_order` 现在指向 V2 正式数据。Hive 表为 EXTERNAL，删除元数据不会自动删除数据，但任何表删除、HDFS 路径清理或正式 Bootstrap 重跑仍需单独授权。M3 在 Day 62～90、跨日恢复和连续回补完成前保持 `in progress`。

### 回滚方式

仓库提供 `hive/ods/rollback_archive_pilot_20260921.sql`。只有正式同名表已按单独授权移除并确认不会丢失正式数据时，才能把 Pilot HISTORY 名称恢复为原名；不得为回滚直接删除 `/warehouse/ecommerce/ods/` 或旧 Pilot HDFS 数据。
