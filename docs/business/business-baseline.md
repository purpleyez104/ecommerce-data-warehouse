# 自营电商业务基线（Business Baseline）

> 文档状态：当前业务规则基线；2026-09-18 整理。来源：本项目对话中用户逐轮确认的业务决策。此文件不是业务系统已经上线的证明。
> 使用优先级：明确的用户确认 > 较新阶段的同项设计 > 较旧候选方案。旧虚拟机的 19 表候选 DDL、Seed、Generator 不作为本版本依据。
> 关联文档：[指标口径](metrics.md) · [逻辑模型](../source/logical-model.md) · [物理模型](../source/physical-model.md)。

## 1. 目标、业务性质与边界

- 经营模式：**自营商城**；模拟业务系统产生真实的业务状态及交易数据，不以第三方真实商户数据为前提。
- 总体覆盖：标准电商版，**分两期实施**。一期实现用户/匿名身份、SPU/SKU、商品展示与行为、购物车、下单/取消、订单券、支付与基础退款，形成资金闭环。二期扩展库存流水/快照、完整履约物流、复杂营销及更完整售后；一期保留 SKU 库存属性概念，不宣称已有库存流水。
- 分析优先方向：交易、流量与转化、商品、用户、退款与售后、营销。
- 数据来源：模拟交易服务写入 MySQL；行为事件独立生成并写入 Kafka。**业务交易 CDC 必须来自 MySQL Binlog，不能由生成器直接写 Kafka 冒充 CDC。**
- 数据规模分为两档，不使用 V1/V2 作为规模名称，也不建设独立 Smoke 档位。正式数据规模为 90 天历史、100,000 笔订单、约 285,000 条订单明细、约 100 万条 OLTP 记录和 3,000,000～5,000,000 条行为事件；性能实验规模为约 900,000 笔订单和 9,000,000 条行为事件。两档均使用显式 Seed 和时间参数，采用历史批量 + 持续增量及可配置的非均匀分布；以上是设计目标，不是实测吞吐。
- 业务统计时区：Asia/Shanghai，按北京时间自然日；实时指标端到端时效开发目标 ≤5 分钟；T+1 经营日报次日 10:00 前（均待实际压测与验收）。

## 2. 术语

| 术语 | 定义 | 示例 |
|---|---|---|
| 实体 | 持续可识别的业务对象 | 用户、SKU、订单、优惠券实例 |
| 业务过程 | 一类实际活动 | 创建订单、支付、退款 |
| 业务事件 | 某个过程发生的一次实例 | 订单 O1 12:00 成功支付 |
| 当前状态 | 某实体当前生命周期位置 | 订单 `PAID` |
| 状态历史 | 带标识和时间的关键变化记录 | `CREATED → PAID` |
| SPU | 商品款式/共享属性的聚合 | 同款手机 |
| SKU | 具体可售规格、定价和库存单位 | 手机-黑色-256G |
| 支付尝试 | 一次向资金通道发起支付的执行 | 第 2 次尝试成功 |
| 资金交易 ID | 每次资金尝试独立且稳定的标识 | 同次重复通知沿用同一 ID |
| Refund Request | 对某一订单明细提出的一笔退款申请 | 对耳机明细申请退 100 元 |
| Refund Transaction | 执行某次退款申请的资金尝试 | 首次失败后新建第 2 次尝试 |
| 业务时间/记录时间 | 事件实际发生/源系统持久化时刻 | 跨天迟到修正依业务时间归属 |

## 3. 一期正常购物流程

```text
匿名访客/登录用户 → 浏览页面 → SKU 曝光/点击 → 加购/移除
  → 结算时重查 SKU 当前售价、可售状态及优惠有效性
  → 创建订单头 + 1~5 条不重复 SKU 明细 + 优惠分摊
  → 订单 CREATED；可选优惠券 UNUSED→LOCKED；截止时间=创建后 15 分钟
  ├─ 主动/超时取消 → CANCELED；锁券释放为 UNUSED 或 EXPIRED
  └─ 一次或多次支付尝试 → 至多一次有效 SUCCESS → PAID；优惠券 USED
        → 可针对某个订单明细申请基础退款
        → 退款资金尝试失败可重试 → 单申请最终全额成功或失败
```

其中支付成功与订单取消竞争时必须在事务和条件校验下产生一个合法最终结果；已支付订单不能通过取消恢复 GMV，只能走退款流程。行为漏斗与交易资金事件是不同统计对象，不可混算。

## 4. 已确认业务规则（按领域）

### 4.1 身份、用户、行为与会话

1. 支持注册用户及匿名访客，行为包含页面浏览、商品曝光、商品点击、加购和移除购物车；保留 user_id、visitor_id、session_id（按事件适用性）。
2. Session：同一访客按**事件时间**连续 30 分钟无活动即结束；后续活动开启新会话。一期由生成器管理/携带 session_id，不额外创建 MySQL Session 表。
3. 匿名与登录统一识别 UV：只有明确登录等可靠证据才能追溯合并；同一 visitor_id 关联多个账号时绝不把不同账号合并，归属不明事件保留匿名。
4. 身份映射修订产生版本及修订记录，可按指定版本追溯回算受影响的 UV、7 日漏斗；不能悄悄覆盖旧已发布结果。
5. 日经营漏斗与按同一批身份严格按顺序完成的群组漏斗同时保留。群组漏斗从首次符合条件的入口事件开始观察 7×24 小时；第一期只要求商城整体漏斗，不强制每个环节是同一 SKU。订单→支付必须关联同一订单。

### 4.2 商品、购物车与订单

1. Category 1:N SPU 1:N SKU；SKU 独立价格和库存，商品价格、类目、品牌、状态的变更留关键历史，为 DIM SCD Type 2 提供源依据。
2. 一单允许 1~5 条订单明细；同一订单的 SKU **不重复**，相同 SKU 用 quantity 表达。第一期不拆单。
3. 购物车登录合并按 SKU 数量相加，单 SKU 上限 99；超限裁剪至 99，记录超出数量和原因；同一合并操作重试不得再次累加。
4. 结算时按最新合法售价和销售状态计算，创建订单时冻结 SKU 单价、名称、SPU/类目/品牌与金额快照；后续改价不改变既有订单。
5. 订单级最多一张简单优惠券，按照确认的确定性比例分摊方法以**分为单位**分到各明细，尾差固定归属，分摊总额与订单优惠完全一致。
6. 金额不变量：订单原价 = Σ(明细单价×数量)；订单应付 = 原价 − 优惠 = Σ明细应付；所有金额非负，不使用浮点金额做财务运算。
7. 订单状态首期为 `CREATED / PAID / CANCELED`；`CREATED→PAID` 或 `CREATED→CANCELED`；已支付不取消。退款状态与订单状态分离。
8. 订单支付有效期 15 分钟；跨越截止时的支付成功与超时取消必须通过业务时间、外部支付结果及互斥事务处理，不能形成同时有效的两个终态。边界时点/异步竞态的实现细节在 DDL 与服务代码验收时明确。

### 4.3 支付与资金

1. 支付允许失败重试：每次尝试新 attempt_id、独立 funding_txn_id；同一次尝试的重复通知沿用同一个 funding_txn_id。
2. 每单至多一次**有效成功**支付；失败尝试保留，但不作为支付成功金额；支付回调以稳定业务/回调标识幂等。
3. 成功金额与订单应付金额一致；支付成功更新订单、支付尝试及关键历史事件时按一个业务事务保持一致，不采用 MySQL+Kafka 应用双写。
4. 现金流按支付和退款**各自成功发生日**归属；订单累计净支付以原订单群组和指定截止时点归属，二者是不同分析视角。

### 4.4 退款与优惠券

1. 第一期支持基础退款；一次退款申请仅关联**一条订单明细**，同一明细允许多次申请；累计成功退款及处理中预留金额不得超过该明细优惠后应付金额。
2. 一笔申请最终完整成功或失败，**不支持同一申请分批成功**；资金失败重试产生新的退款尝试和独立资金交易标识，同一笔成功只入账一次。
3. 支持纯金额补偿，退款件数只计入有明确退款数量且已实际成功的申请；不能通过退款金额反推件数。
4. 优惠券：订单创建时有效即可锁定。有效锁定保留至订单 15 分钟截止，即使其自身有效期在期间到期仍可正常支付；取消释放时已过期则 `EXPIRED`，否则 `UNUSED`。
5. 核销后状态 `USED`，**即使全额退款也不返券**。券领取、锁定、核销、释放及优惠金额均可追踪。
6. 退款率同时保留指定截止时点累计口径与订单创建后 30 日固定观察窗口口径；未成熟群组不能冒充完整 30 日样本。

## 5. 核心事实与金额示例

订单含 SKU-A 1 件×3000 元、SKU-B 2 件×200 元，原价 3400 元，订单券减 300 元：

| 明细 | 原价（元） | 分摊优惠（元） | 应付（元） |
|---|---:|---:|---:|
| A | 3000.00 | 264.71 | 2735.29 |
| B | 400.00 | 35.29 | 364.71 |
| 合计 | 3400.00 | 300.00 | 3100.00 |

支付成功 3100 元、B 全额退款 364.71 元后，订单累计净支付=2735.29 元；但 GMV 是否变动仍遵守指标 V2.0：**取消订单回冲原下单日，退款独立记录，不等同于取消。**

## 6. 异常场景与可验收不变量

| 场景 | 预期行为 |
|---|---|
| 首次支付失败、再次成功 | 两次尝试、最多一次有效成功，订单最终 PAID |
| 同一支付成功通知重复 | 资金 ID/事件 ID 去重，不重复入账 |
| 订单超时与支付成功竞争 | 仅有一个有效结果，订单/支付/券历史一致 |
| 已锁优惠券过期 | 订单期限内允许付款；取消则按是否过期释放或失效 |
| 全额退款 | 券保持 USED；订单保持 PAID，退款独立核算 |
| 同明细多次退款 | 成功+预留+本次 ≤ 该明细应付金额 |
| 金额补偿 | 退款额可有，退款件数不推断 |
| 购物车 60+50 | 合并为 99，截断 11，重复合并无再次累加 |
| 游客关联多账号 | 无可靠证据的归属不合并账户，保持匿名 |
| 改价后查询历史订单 | 使用订单明细价格快照；商品历史变更可重建 |
| 跨天取消/退款、迟到行为 | 事件时间归属 + 有版本的受影响窗口修正 |

## 7. 数据生成与验收

- 生成器：Python 模块化单体，共用状态机；历史批量 + 后续持续增量；业务交易通过 MySQL 提交，行为通过独立 Kafka 事件接口输出。
- 模拟参数：每日订单量/行为量、订单 1~5 明细分布、热门 SKU、活跃用户、日订单波动、支付率、失败重试、取消、退款申请、用券率，均可配置；未确认的**具体概率不写作既成事实**。
- 正式数据规模直接承担业务规则、正反例和指标可计算性验收；不再为新 Generator 单独生成约 100 单的 Smoke 数据档位。性能实验规模只在正式数据规模通过后用于专项压测，实际性能另验。
- 数据链路：MySQL 当前状态 + 专用历史表，以同一事务持久化；Flink CDC 从真实 Binlog 采集；行为按页面/商品/购物三组 Topic；优先一致性快照+CDC 接续。

## 8. 实施边界与未决工程项

此文件是**业务基线**，不是已生成的 SQL/部署成果。正式数据运行已使用显式 Seed `20260928`，但业务基线不把某个 Seed 写成业务语义。以下保持未决：库存字段落地与商品变更事件 JSON 的精确 Schema、行为 Topic 最终名称/分区/保留策略、各种业务执行事务的锁顺序、支付截止边界的最终代码判定、DataX 与 CDC 双链路初始化去重/对账机制。均不能默认为已验收。

## 9. 变更控制

改变业务口径先更新此文件及 `../metrics.md`，再改逻辑模型、物理模型、测试/DDL；新增状态、指标、表需显式记录版本和影响范围。历史 19 表候选实现不应直接覆盖当前 21 表设计。
